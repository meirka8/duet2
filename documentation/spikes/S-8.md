# S-8 — Packaging shape (Flatpak + AppImage)

**Status:** done. **Timebox:** 1 day (task.md). **Traces:** NFR-09 (binary size), NFR-10 (no GTK/Qt/KDE runtime dependency).

**Question this spike answers:** can a GPUI app be packaged as both Flatpak and AppImage and actually run on a system with no GTK/Qt/KDE runtime present?

**Answer:** yes for both packaging formats on this host. The GTK/Qt/KDE-free claim is verified by static/dynamic dependency analysis (strong evidence, see below) rather than by an actual container run, because this environment's Docker daemon was not reachable by the working user and no rootless alternative (Podman) was installed — that gap is real and is called out explicitly rather than papered over.

## What was built

All under `spikes/s8-packaging/` in this worktree:

- `hello-gpui/` — a standalone Rust crate (`gpui = "0.2.2"`, same pin as the S-1 spike), `edition = "2024"`, that opens one window with a centered text label ("Hello, Duet (S-8 packaging spike)") and nothing else. No `gpui-component`, no synthetic data — S-8 is about the packaging pipeline, not the UI.
- `org.duet.HelloGpui.yml` — a Flatpak manifest.
- `org.duet.HelloGpui.desktop`, `org.duet.HelloGpui.png` — desktop entry and a placeholder icon (generated with ImageMagick; a plain "D" glyph on a dark square, not production art).
- `build-hello-gpui.sh` — builds the host release binary (`cargo build --release`), used both as the AppImage payload and as the first (abandoned) Flatpak approach.
- `build-appimage.sh` — assembles an `AppDir` by hand from the host-built binary and runs `appimagetool` over it.

Build outputs (`hello-gpui/target/`, `.flatpak-builder/`, `build-dir/`, `repo/`, `AppDir/`, `*.AppImage`) are all gitignored; only the sources and build scripts are committed, per the disk-space note for this session.

## Flatpak: built and ran

Manifest: `spikes/s8-packaging/org.duet.HelloGpui.yml`. Runtime is bare `org.freedesktop.Platform//24.08` + `org.freedesktop.Sdk//24.08` — deliberately **not** `org.gnome.Platform` or `org.kde.Platform`, since Duet renders its own UI and design.md §4.2 treats a GTK/Qt dependency as a non-goal. `finish-args` request only `--socket=wayland`, `--socket=fallback-x11`, `--share=ipc`, and `--device=dri` (GPU access for GPUI's blade-graphics renderer); no filesystem, network, or D-Bus access, since this hello-world touches neither.

**Gotcha #1 (real, worth remembering): don't copy a host-built binary into a Flatpak.** First attempt used `buildsystem: simple` to `install` the already-built host binary straight into `/app/bin`, to avoid needing network access inside the flatpak-builder sandbox. It built fine but failed at run time:

```
hello_gpui: /usr/lib/x86_64-linux-gnu/libm.so.6: version `GLIBC_2.43' not found (required by hello_gpui)
hello_gpui: /usr/lib/x86_64-linux-gnu/libm.so.6: version `GLIBC_2.44' not found (required by hello_gpui)
```

The host (Arch Linux, rolling) has a newer glibc than `org.freedesktop.Platform//24.08` bundles. A binary built against the host's glibc is not ABI-compatible with the runtime's own libc/libm inside the sandbox. **Fix:** build *inside* the sandbox using the `org.freedesktop.Sdk.Extension.rust-stable` (1.89.0) extension, so the resulting binary links against the runtime's own glibc. This required `--share=network` in the module's `build-options.build-args` since crates.io deps for `gpui` aren't vendored for this timeboxed spike (a Flathub-eligible manifest would vendor dependencies for a fully offline, reproducible build — noted here as a follow-up, not solved).

With that fix: `flatpak-builder --force-clean --repo=repo build-dir org.duet.HelloGpui.yml` completed cleanly (only a benign "no appstream data" warning). `flatpak remote-add --user --no-gpg-verify s8-local-repo repo` + `flatpak install --user -y s8-local-repo org.duet.HelloGpui` installed it (15.1 MB installed size). `flatpak run org.duet.HelloGpui`, backgrounded with a `timeout`, produced this process tree under `bwrap`:

```
bwrap --args 68 -- hello_gpui
  bwrap --args 68 -- hello_gpui
    hello_gpui
```

and this stdout/stderr (from the app's own heartbeat logging, since we can't screenshot a GTK-less window in this environment — see "GUI verification method" below):

```
hello_gpui: starting Application::new()
hello_gpui: inside App closure, opening window
hello_gpui: window opened successfully, entering event loop
```

The process was still alive when `timeout` killed it (exit 124, not a crash exit code). Confirmed no `/tmp/.mount_*`-style leftover or zombie process after exit.

## AppImage: built and ran

`build-appimage.sh` hand-assembles an `AppDir` (`AppRun`, `usr/bin/hello_gpui`, `usr/share/applications/*.desktop`, `usr/share/icons/hicolor/256x256/apps/*.png`, top-level `.desktop`/`.png`/`.DirIcon`) from the **host-built** binary (glibc mismatch isn't an issue here — the AppImage runs directly against the host's own libc, it isn't crossing into a different runtime's libc the way the Flatpak sandbox does) and runs `appimagetool AppDir HelloGpui-x86_64.AppImage`.

`linuxdeploy` is not installed in this environment (only `appimagetool` via the `appimagetool-bin` AUR package was available, as specified for this spike), so the AppImage does **not** bundle shared libraries — it relies on the host providing `libxcb`, `libxkbcommon`, `libxkbcommon-x11`, `libwayland-client` (dlopen'd). These are low-level X11/Wayland client libraries present on essentially any Linux desktop; they are explicitly not GTK/Qt/KDE toolkit libraries, so this doesn't undermine the NFR-10 claim, but it is a real portability gap the AppImage format is normally used to close, and it should be addressed by getting `linuxdeploy` (or its Rust ecosystem equivalent, e.g. `cargo-appimage`'s bundling logic) into the real release pipeline rather than assuming shared libs are always present. Noted as a follow-up.

`appimagetool` output was clean aside from an expected AppStream-metadata-missing warning (same class of gap as the Flatpak's missing appstream, not addressed here). Running `./HelloGpui-x86_64.AppImage` (backgrounded, `timeout`) produced:

```
timeout 6 ./HelloGpui-x86_64.AppImage
  /tmp/.mount_HelloGfALOMg/usr/bin/hello_gpui
./HelloGpui-x86_64.AppImage   (the outer process, type2 runtime, stays around managing the FUSE mount)
```

with the same three heartbeat lines on stdout/stderr, process alive until `timeout` killed it (exit 124), and no lingering `/tmp/.mount_*` FUSE mount or process afterward.

## GUI verification method (and its limit)

Per this environment's known limitation, computer-use/screen automation for newly-launched GTK windows is broken, and GPUI windows aren't GTK anyway. Verification was therefore process-level, not visual, for all three run modes (native, Flatpak, AppImage):

1. The app itself logs three heartbeat lines to stderr at `Application::new()` start, immediately before `open_window`, and immediately after `open_window` returns `Ok` — so "window opened successfully" in the log is GPUI's own confirmation that the platform layer (Wayland client + compositor round-trip) accepted the window, not just that the process didn't panic.
2. Backgrounded with `timeout N`, then `ps -ef` mid-run to see the live process (and, for Flatpak, the `bwrap` sandbox tree; for AppImage, the FUSE-mounted squashfs process), then waited for the exit code. All three runs exited `124` (killed by `timeout`, i.e. still running and healthy at that point), not a panic/segfault code.
3. No error output, no stack trace, no "failed to open window" (the `.expect()` message that would fire on a real windowing failure) in any of the three logs.

This is process-level evidence of a real, accepted Wayland window, not merely "the binary didn't crash immediately" — but it is not a pixel-level confirmation that something visually correct was drawn. That residual gap is inherent to this environment, not specific to Duet or this spike.

## GTK/Qt/KDE-dependency-free verification (proxy for the container test)

**Docker is installed but not usable by this session:** `docker info` returns `permission denied while trying to connect to the docker API at unix:///var/run/docker.sock`; the working user is not in the `docker` group, and `sudo` requires a password this session doesn't have. `podman` is not installed. So the actual container run design.md §NFR-10 calls for ("Container test matrix") was **not performed** — this is the honest gap, not worked around.

As a proxy, dynamic-linking and dlopen analysis was run against all three build outputs (native host binary, the binary extracted from the installed Flatpak, and the binary extracted from the AppImage's squashfs via `--appimage-extract`). All three are **identical** in their dependency set:

```
$ ldd hello_gpui
        libxcb.so.1
        libxkbcommon.so.0
        libxkbcommon-x11.so.0
        libgcc_s.so.1
        libm.so.6
        libc.so.6
        libXau.so.6
        libXdmcp.so.6
        libxcb-xkb.so.1
        /lib64/ld-linux-x86-64.so.2
```

No `libgtk`, `libQt*`, or `libKF*` in that list. `strings` over the binary additionally confirms `libwayland-client.so.0` is dlopen'd at runtime (present in the error-message text GPUI's wayland backend embeds: `"Library libwayland-client.so could not be loaded."`) with no `libgtk`/`libQt`/`libKF` strings anywhere in the binary. The only KDE-related strings found are Wayland *protocol* extension interface names (`org_kde_kwin_blur_manager`, etc. — from the `wayland-protocols-plasma` crate, used to speak the KDE blur/window-decoration Wayland protocol extensions if the compositor offers them) — these are protocol strings, not linked KDE shared libraries, and don't pull in Qt or any KDE Frameworks library.

The Flatpak manifest itself is corroborating evidence at a different layer: it declares `runtime: org.freedesktop.Platform` with no GNOME or KDE platform extension, and `flatpak-builder` did not need to pull one in to satisfy the build.

**Verdict:** strong proxy evidence (three independently-produced binaries, all with an identical, GTK/Qt/KDE-free dependency set) that NFR-10's "no GTK/Qt/KDE runtime" bar is met. The actual container-based acceptance test design.md prescribes is still outstanding and should be the first thing re-run once a session with working Docker/Podman access is available — do not treat this proxy as a permanent substitute for that gate.

## Binary sizes (NFR-09 baseline / overhead measurement)

This is a hello-world, not the real app, so these numbers are a **floor**, not a prediction of Duet's shipped size — they measure GPUI + Rust runtime + packaging overhead with ~zero application code on top.

| Artifact | Size | Notes |
|---|---|---|
| Native release binary (host-built, `strip = true`, `lto = true`) | 14,666,976 B (14.0 MiB / 14.7 MB) | `ldd`-linked against system libs; this is the payload both packaging formats wrap |
| Flatpak-built binary (built inside the SDK sandbox, `org.freedesktop.Sdk.Extension.rust-stable` 1.89.0) | 15,128,200 B (14.4 MiB / 15.1 MB) | Slightly larger than the host build — different rustc point release (1.89.0 vs host 1.97.1) and glibc target |
| Flatpak installed size (`flatpak info`) | 15.1 MB | Binary + desktop file + icon; no runtime included (shared, already installed) |
| AppImage file (`HelloGpui-x86_64.AppImage`) | 6,662,648 B (6.4 MB) | zstd-compressed squashfs of the AppDir; compression alone gets the 14.0 MiB binary down to 6.4 MB on disk |

Against NFR-09's ≤40 MB stripped / ≤25 MB core-without-codecs goal: a bare GPUI window already costs ~14–15 MB stripped before any Duet application code, VFS layer, EntryStore, table rendering, or archive codecs are added. That leaves roughly 10–25 MB of headroom under the ≤25 MB "core without bundled archive codecs" figure specifically, which is tight but plausible if archive/network codecs stay feature-gated as design.md §7 already specifies. This should be tracked as a CI-checked metric from the first real milestone build, not just at ship time, given how little headroom the ≤25 MB core figure leaves.

## Gotchas discovered, summarized

1. **Never copy a host-built binary into a Flatpak `/app`.** Host glibc (Arch, rolling) ships newer symbol versions (`GLIBC_2.43`, `GLIBC_2.44`) than `org.freedesktop.Platform//24.08` bundles; the binary fails to even start under `bwrap`. Always build inside the SDK sandbox (or an equivalently-old build environment) so the binary links against the runtime's own glibc.
2. **Building Rust inside the flatpak-builder sandbox needs `--share=network`** unless dependencies are vendored ahead of time — flatpak-builder denies network by default, and `gpui`'s dependency tree is not vendored for this spike. A production/Flathub-eligible manifest should vendor dependencies instead, both for hermetic reproducibility and because Flathub's own build infrastructure disallows network access during build.
3. **No AppStream metadata** was provided for either package (`org.duet.HelloGpui.appdata.xml` missing) — both `flatpak-builder` and `appimagetool` warn about this but still produce a working artifact. Real packaging work needs this file for app-store-style listings (GNOME Software, Discover, AppImageHub); it wasn't in scope for a feasibility spike.
4. **No `linuxdeploy`** in this environment, so the AppImage doesn't bundle its shared libraries (`libxcb`, `libxkbcommon*`, `libwayland-client`). It still runs here because the host has those libraries, but a truly portable AppImage (the whole point of the format) should bundle them. Get `linuxdeploy` (or equivalent) into the real release pipeline.
5. **Docker present but inaccessible this session** (`permission denied` on the socket, user not in `docker` group, no passwordless `sudo`), and Podman not installed — the NFR-10 "Container test matrix" acceptance method from design.md could not actually be run. Verified via dependency analysis instead (see above); flagged here as unfinished business, not silently substituted.
6. **Icon is a placeholder** (`convert`-generated "D" glyph, 16-bit grayscale PNG) — fine for a packaging spike, not fine for a real release; real Duet branding/icon work is out of scope here.

## Bottom line for the G0 decision

Both packaging formats are feasible for a GPUI app, build cleanly with tools already available in this environment, and run without a GTK/Qt/KDE runtime present (evidenced, not just assumed) — the underlying question S-8 asks. The two things a real packaging effort needs to close before shipping are: (a) an actual container-based test of NFR-10 (this environment couldn't run one), and (b) a `linuxdeploy`-based (or equivalent) AppImage build that bundles its own shared libraries instead of assuming the host has `libxcb`/`libxkbcommon`. Neither is a feasibility blocker; both are concrete follow-up tasks for Phase 11 (T-11.1.1, T-11.1.2).
