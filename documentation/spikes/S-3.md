# S-3 — Cross-application drag & drop

**Status:** harness built, source-level investigation complete. **Interactive cross-app
testing (Nautilus / a terminal / Firefox) NOT yet performed** — that part requires live
desktop control and is deliberately out of scope for the agent that built this harness.

**Preliminary verdict from source inspection (subject to interactive confirmation below):**
**inbound** cross-app DnD (files/URIs dragged from Nautilus, Firefox, etc. *into* Duet) is
**natively supported by GPUI 0.2.2** on both Wayland and X11 — no fallback needed.
**Outbound** cross-app DnD (dragging Duet's own rows *out* to another application) has **no
implementation anywhere in gpui 0.2.2's Linux backends** and is recommended for **defer to
P1**, per the reasoning below (this is one of the two AC-acceptable outcomes for S-3: "verdict
+ prototype or a documented 'defer to P1' recommendation with the reason").

## Investigation method

Rather than trust crate docs/examples (gpui-component ships no DnD example), the actual
`gpui-0.2.2` source was read directly from the local cargo registry cache
(`~/.cargo/registry/src/*/gpui-0.2.2/src/`), grepping for `drag`/`dnd`/`drop` across the whole
crate, then reading the matching code paths in full:

- `src/interactive.rs` — `FileDropEvent` enum (`Entered`/`Pending`/`Submit`/`Exited`),
  `ExternalPaths` (a `SmallVec<PathBuf>` wrapper whose inner field is `pub(crate)`, i.e.
  application code cannot construct one directly — only the platform layer can).
- `src/window.rs` (~line 3620) — `Window::handle_input`'s `PlatformInput::FileDrop` arm
  translates real OS drop events into GPUI's own `App::active_drag` mechanism (the *same*
  state ordinary same-window `on_drag`/`on_drop` uses), then synthesizes `MouseMove`/`MouseUp`
  so the normal hit-testing/`on_drop::<ExternalPaths>` dispatch just works. This is the key
  finding: **inbound OS drops and in-app drags share one code path** in GPUI.
- `src/elements/div.rs` — the public `on_drag`/`on_drag_move`/`on_drop`/`can_drop`/`drag_over`
  API. Confirmed this is a **synthetic, in-process** mechanism: `on_drag` just registers a
  constructor for a preview view and stashes an `Arc<dyn Any>` value in `cx.active_drag`;
  drop targets are resolved via ordinary mouse-move hit-testing against that state. Nothing
  here calls into any platform/windowing API — it cannot, by itself, exchange data with
  another process.
- `src/platform/linux/wayland/client.rs` — the **real Wayland target-side implementation**:
  imports `wl_data_device`, `wl_data_device_manager`, `wl_data_offer`, `wl_data_source`;
  implements `Dispatch<wl_data_device::WlDataDevice, _>` handling `Enter`/`Motion`/`Leave`/
  `Drop` events, calls `data_offer.receive("text/uri-list", pipe_fd)`, reads the URI list off
  the pipe, parses each line with `Url::parse(..).to_file_path()`, and emits
  `PlatformInput::FileDrop(FileDropEvent::Entered { paths, .. })`. `FILE_LIST_MIME_TYPE` is
  defined in `wayland/clipboard.rs` as `"text/uri-list"`.
  **No call to `data_device.start_drag(...)` exists anywhere in the file** — the only
  `create_data_source` call in the whole crate is for the **clipboard** (`set_selection`),
  not for a DnD source.
- `src/platform/linux/x11/client.rs` — the **real XDND target-side implementation**: a
  `Xdnd` state struct, handling `XdndEnter`/`XdndPosition`/`XdndDrop` window messages, replying
  with `XdndStatus`/`XdndFinished`, retrieving `XDND_DATA` via the X selection mechanism, and
  emitting the same `FileDropEvent`. Again, no XDND **source**-side logic (no code sends
  `XdndEnter`/`XdndPosition` as the initiator) exists anywhere in the crate.
- `gpui::Window` implements `raw_window_handle::HasWindowHandle`/`HasDisplayHandle`
  (`src/window.rs`, delegating to `PlatformWindow`), and the Wayland backend's impl
  (`platform/linux/wayland/window.rs`) returns the **real, live** `wl_surface*`/`wl_display*`
  GPUI itself is using (via `wayland_backend`'s `Backend::display_ptr()`), not a dummy handle.

## What this means, concretely

| Direction | Mechanism | Status |
|---|---|---|
| External app → Duet window (drop) | `wl_data_device` (Wayland) / XDND (X11) target, native in gpui, surfaces as `on_drop::<ExternalPaths>()` | **Works natively, both protocols.** No fallback needed. |
| Duet window → external app (drag out) | Nothing — GPUI's `on_drag` never touches `wl_data_device`/XDND source APIs | **Not implemented in gpui 0.2.2.** |
| Duet row → Duet's own drop zone (same window) | GPUI's synthetic `on_drag`/`on_drop` via `active_drag` | Works, but is **not** cross-app — included in the harness only as a UI sanity check / visual reference for the tester. |

### Why outbound wasn't bolted on with smithay-client-toolkit in this spike

The task brief anticipated a fallback of "raw Wayland `wl_data_device`/XDND through
`smithay-client-toolkit` running alongside the window." Two shapes of that were considered:

1. **A fully independent second Wayland connection/window**, using SCTK to open its own
   little surface purely as a drag handle. This is safe (zero interference with GPUI's event
   loop) and would technically satisfy "drag out of *a* window," but it is not dragging out of
   *Duet's actual UI* — the row a user drags would live in a separate helper window, which
   doesn't match the product requirement (FR-CFG-06 expects dragging real Duet rows).
2. **Reusing GPUI's own live Wayland connection**, discovered via `Window`'s
   `raw_window_handle` (`HasDisplayHandle` returns the real `wl_display*`; `HasWindowHandle`
   the real `wl_surface*`). This is the only shape that could produce a drag that visibly
   originates from Duet's own row and lands correctly positioned in another app. It was **not
   attempted live** in this spike: `wayland-backend`'s `Connection`/event-queue types own the
   read/dispatch cursor of the underlying socket fd internally; wrapping the same raw
   `wl_display*` a second time in an independently-owned Rust `Connection`/`EventQueue` and
   driving both from separate call sites is an unsupported, undefined-behaviour-risking
   arrangement (races on `wl_display_prepare_read`/`read_events`, potential dropped/duplicated
   events) that could destabilize GPUI's own rendering/input loop. Given this spike's own AC
   requires confirming the binary "launches without crashing," deliberately introducing that
   risk into a 3-day timeboxed spike was judged not worth it.

**Recommendation: defer real outbound cross-app drag to P1**, scoped as either (a) an upstream
contribution to `gpui` itself adding `wl_data_device::start_drag`/XDND-source support behind
the existing `on_drag` API (the architecturally correct fix — GPUI already owns the connection
cleanly, so the fix belongs on their side of the raw-pointer boundary), or (b) if upstreaming
stalls, a dedicated (non-timeboxed) engineering effort to properly synchronize a second
Wayland client against GPUI's connection, which needs real design and testing, not a spike-day
attempt. This matches R-G3's documented fallback shape ("degrade to P1-deferred if only
intra-app DnD is achievable for 1.0").

## What was built

`spikes/s3-dragdrop/` — a standalone Cargo binary (`gpui = "0.2.2"`, `gpui-component =
"0.5.1"`, same pinned versions as S-1) with a single-window app (`src/main.rs`):

- On startup, creates a real fixture file at `/tmp/duet-s3-test/drag-me.txt`.
- **Drag source row** ("📄 drag-me.txt"): wired with GPUI's `on_drag`, carrying a private
  `InAppDragPayload { path }`. Dragging it shows a small blue "drag-me.txt" ghost that follows
  the cursor. This drag is same-window only, per the findings above — it will **not** produce
  anything a compositor-level drag-and-drop target outside the window can see.
- **Drop target box**: registered with `on_drop::<ExternalPaths>()` (the real,
  platform-native path fed by actual Wayland/X11 drops from other applications) *and*
  `on_drop::<InAppDragPayload>()` (the in-app demo drag above), plus `drag_over` styling
  (background turns green while something is hovering over it) for both. Every accepted drop
  is appended to an on-screen, newest-first log and also printed to stdout as
  `[drop-zone] ...`.

## Build & run

```sh
cd spikes/s3-dragdrop
cargo build            # confirmed: builds clean against crates.io gpui 0.2.2 / gpui-component 0.5.1
./target/debug/s3_dragdrop
```

Confirmed during harness construction: the binary builds with no errors/patches/vendoring,
and launches and stays alive (tested with a backgrounded, timeout-bounded run — process
stayed in sleeping/running state for the full duration with no stderr output and no crash).
Window title: **"s3_dragdrop"** (GPUI's default `WindowOptions` — no custom title was set,
so expect the binary name / whatever GPUI derives; if the compositor shows something else,
that's the actual title to look for). Binary: `s3_dragdrop` at
`spikes/s3-dragdrop/target/debug/s3_dragdrop`.

## Manual interactive test script (for the orchestrator — not run by this agent)

Session is Wayland (`XDG_SESSION_TYPE=wayland`); also worth a quick X11 sanity pass if an
Xwayland/X11 session is easily available, since the source-level finding above claims parity
between the two backends.

1. Run `./target/debug/s3_dragdrop` from `spikes/s3-dragdrop/`. Confirm a window titled
   "s3_dragdrop" (or similar) opens showing a dark UI with a "drag-me.txt" row near the top
   and a bordered "Drop target" box below it.
2. **In-app sanity check (expected to work):** drag the "drag-me.txt" row down onto the drop
   target box. Confirm the box's border/background flashes green while hovering, and on
   release a line "in-app drag received: /tmp/duet-s3-test/drag-me.txt" appears in the log
   (and in the terminal running the app).
3. **Outbound, Duet → Nautilus (expected to fail per source inspection):** open a Nautilus
   window at `/tmp/duet-s3-test`. Drag the "drag-me.txt" row from Duet onto the Nautilus
   window. Expected: nothing happens in Nautilus (no file appears/copies); the drag likely
   just shows GPUI's in-app ghost briefly or nothing at all once the cursor leaves Duet's
   window. Record what actually happens (does the cursor even show a drag icon over
   Nautilus?).
4. **Outbound, Duet → terminal (expected to fail):** open a terminal emulator. Drag the
   "drag-me.txt" row from Duet onto the terminal window. Expected: no path gets typed/pasted.
   Record actual behaviour.
5. **Inbound, Nautilus → Duet (expected to work):** in Nautilus (any directory), drag a file
   onto Duet's drop target box. Confirm a line like "OS drop received (text/uri-list):
   file:///path/to/file" appears in Duet's log.
6. **Inbound, Firefox → Duet (expected to work):** open Firefox to any page with an image.
   Drag the image into Duet's drop target box. Confirm a `file://...` or `http(s)://...` URI
   (Firefox may offer a remote URL rather than a local path if the image isn't cached as a
   file) appears in the log. Note whether Firefox offers a usable `text/uri-list` at all, or
   only e.g. `text/x-moz-url` — if the log stays empty, note that as a real finding (GPUI's
   Wayland client only requests `text/uri-list` specifically, per `FILE_LIST_MIME_TYPE`; if a
   source app doesn't offer that mime type, the drop is silently dropped — see
   `wayland/client.rs`'s "Prevent dropping text from other programs" comment/`paths.is_empty()`
   early-return).
7. Repeat steps 3–6 under X11 (Xwayland or a native X11 session) if convenient, to confirm the
   source-level parity claim about GPUI's X11 XDND target implementation.
