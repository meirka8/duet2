# S-7 — WASM plugin round trip

**Task:** Load a trivial `wasmtime` component implementing a content plugin
returning one column value; measure per-call overhead.

**AC:** Per-call overhead under 100µs warm; fuel/epoch interruption
demonstrated to actually stop a `loop {}` plugin.

**Traceability:** FR-PLUG-01 (no ambient authority), FR-PLUG-06 (a
misbehaving plugin degrades only its own feature; fuel/epoch limits and
memory caps enforced).

**Code:** `spikes/s7-wasm-plugin/` (WIT, two guest components, host
harness, `build.sh`).

## Verdict

| AC item | Result |
|---|---|
| Per-call overhead under 100µs warm | **PASS** — median 0.76–1.16µs across six runs, p99 1.2–1.4µs (60–130x under budget even at the noisy end) |
| Fuel/epoch interruption stops `loop {}` | **PASS** — epoch interruption traps the runaway call at ~2.0s, host process continues normally |

## Setup

- `wit/content-plugin.wit`: a minimal slice of design.md §9.9's
  `content-plugin` interface — `fields() -> list<field-def>` and
  `value(path: string, field: u32) -> result<field-value, string>`. Path is
  a plain string here (the real interface hands the guest a host-opened
  handle, not a path — see "Findings relevant to FR-PLUG-01" below); the
  simplification keeps the spike focused on the call-boundary cost, which
  is what the AC asks about.
- `guest-content`: implements the interface; `value()` returns the byte
  length of `path` as an integer. Trivial on purpose — the guest's own
  work is not what's being measured.
- `guest-loop`: same interface; `value()` runs `loop { counter =
  counter.wrapping_add(1); black_box(counter); }` forever. Never returns
  on its own.
- `host/src/bench.rs`: instantiates `guest-content`, calls `value()` 1,000
  times to warm up the JIT (discarded), then 200,000 more times, timing
  each call individually with `Instant::now()`/`elapsed()` around exactly
  the `plugin.call_value(...)` invocation (string formatting for the
  per-iteration path happens before the timer starts).
- `host/src/interrupt.rs`: enables `Config::epoch_interruption(true)`,
  sets a 20-tick deadline on the store, spawns a background thread that
  calls `engine.increment_epoch()` every 100ms (~2s to exhaust the
  deadline), then calls `guest-loop`'s `value()` and measures how long
  until the call returns an `Err` (a trap) instead of hanging.

Both guest components compile through `wit-bindgen 0.57`'s `generate!`
macro; the host uses `wasmtime::component::bindgen!` (wasmtime 47.0.3)
against the same WIT file. No hand-written glue.

## Results — per-call overhead

Six runs of `bench` (200,000 measured calls each, 1,000-call warmup
discarded), release build, `wasm_component_model` config, no fuel/epoch
overhead active (bench and interrupt use separate, independently
configured stores/engines). Runs 1–3 were on an otherwise-idle machine;
runs 4–6 happened while a clean rebuild (`build.sh`, cargo compiling
`wasmtime` and friends) was finishing in the background — kept here
deliberately to show the noise floor rather than cherry-picking the best
numbers:

| run | min | median | mean | p99 | p99.9 | max |
|---|---|---|---|---|---|---|
| 1 (idle) | 731ns | 772ns | 863ns | 1192ns | 3086ns | 28.0µs |
| 2 (idle) | 722ns | 762ns | 790ns | 1152ns | 1833ns | 13.4µs |
| 3 (idle) | 721ns | 771ns | 794ns | 1342ns | 4338ns | 32.1µs |
| 4 (contended) | 751ns | 1162ns | 1727ns | 1372ns | 32.7µs | 3.30ms |
| 5 (contended) | 741ns | 1152ns | 1350ns | 1312ns | 10.5µs | 3.11ms |
| 6 (contended) | 941ns | 1163ns | 1296ns | 1343ns | 11.9µs | 3.03ms |

Median holds in the **0.76–1.16µs** range and p99 in **1.15–1.4µs**
regardless of background CPU contention — both 60–130x under the 100µs
budget even at the noisy end. The contended runs' p99.9/max blow out to
tens of microseconds and occasionally milliseconds (a rebuild competing
for cores causes real scheduler stalls), but that's host-machine noise,
not per-call component-model cost, and it doesn't move the median or p99
that the AC is stated against.

**Implication for the motivating scenario** (computing a column value per
row while scrolling/sorting a directory): at ~1µs/call (worst observed
median), 10,000 rows costs ~10ms of pure call overhead — negligible
against a frame budget, and in
practice this would be pipelined/cached per §11 (metadata laziness) rather
than called synchronously per visible row anyway. The call boundary itself
is not the bottleneck; whatever the guest's `value()` implementation
actually does (e.g., real EXIF parsing) will dominate.

## Results — fuel/epoch interruption

```
calling guest-loop's value() (a `loop {}` that never returns); epoch deadline = 20 ticks @ 100ms/tick ~= 2s
guest call was interrupted after 2.001287563s
trap: error while executing at wasm backtrace:
    0:   0x14ef - <unknown>!<wasm function 12>
host process is still alive and able to continue (this line printed after catching the trap, not after a crash/hang).
```

- Elapsed time to interruption: **2.001s**, matching the configured
  20-tick × 100ms deadline almost exactly (epoch checks are injected by
  Cranelift at loop back-edges automatically — the guest needed no
  cooperation, `loop {}` with no host calls inside it was still caught).
- The call returns `Err` (a `wasmtime::Error` wrapping a trap), not a
  panic, process abort, or hang. `timeout 10 ./interrupt` exits `0`
  (clean exit, not the shell's timeout-triggered `124`) — the host
  process is provably still in control of itself after killing the guest
  instance, which is the FR-PLUG-06 requirement ("degrades its own
  feature only").
- Fuel-based interruption (`Config::consume_fuel` + `Store::set_fuel`)
  was not separately exercised in this spike — epoch interruption is the
  mechanism design.md's wall-clock deadline ("2s per call") actually
  calls for, since fuel counts instructions, not time, and would need
  per-plugin calibration to approximate a time budget. Fuel remains
  available in `wasmtime` for cases wanting a deterministic instruction
  ceiling instead; worth a follow-up note in T-8.1.1, not a blocker here.

## Toolchain friction (a real finding, not just plumbing)

This sandbox has no `rustup` and no prebuilt `wasm32-*` std/sysroot, and
no passwordless `sudo` to install the `rust-wasm` pacman package. Getting
from zero to a buildable component required:

1. **`-Z build-std`** to rebuild `std`/`core`/`alloc` from source for a
   target with no prebuilt sysroot — works on stable `rustc` via
   `RUSTC_BOOTSTRAP=1`, and only because `rust-src` happened to be
   installed as a system package. A machine without `rust-src` would be
   stuck.
2. **`wasm32-wasip2` doesn't work this way** — it additionally needs a
   prebuilt `wasi-libc` (`-lc`), which is a C static library, not
   something `-Z build-std` can produce. Linking failed with `unable to
   find library -lc`.
3. **Switched the guest target to `wasm32-unknown-unknown`** instead —
   no libc dependency at all, so `-Z build-std` alone is sufficient. As a
   side effect this target has no WASI import surface whatsoever, which
   is actually a clean demonstration of zero ambient authority for this
   guest (see below) but would need revisiting once real plugins need
   WASI-shaped host calls (clocks, host-provided file streams, etc. —
   design.md's own `host` interface is the intended replacement for raw
   WASI here, not something this spike needed).
4. `wasm32-unknown-unknown` output is a plain core wasm module, not a
   Component — **`wasm-tools component new`** (installed via `cargo
   install wasm-tools`, no adapter needed since there are zero host
   imports) wraps it.
5. The cdylib link step needs the **`wasm-component-ld`** linker binary,
   normally shipped as a rustup component; installed via `cargo install
   wasm-component-ld` instead.

None of this required root or touched anything outside the project/cargo
home. It's captured in `spikes/s7-wasm-plugin/build.sh`, which is the
authoritative reproduction steps. **This exact recipe (build-std +
wasm32-unknown-unknown + wasm-tools component new) will not scale past a
spike**: real content/packer/fs plugins will want `std` conveniences
(alloc-heavy string/JSON work is fine, but anything wanting host-provided
time or the `host` interface's file handles needs an explicit import, not
ambient WASI), and third-party plugin authors won't want to hand-roll
`-Z build-std` incantations. T-2.6.1/T-8.1.1 should either (a) get CI/dev
machines a proper `rustup target add wasm32-wasip2` + `wasm-component-ld`
setup (the "real" path, blocked here only by lack of sudo), or (b) budget
time to script this workaround into `duet plugin` tooling. Recommend (a)
for the actual project — this spike's workaround is a sandbox artifact,
not a recommendation.

## Findings relevant to FR-PLUG-01 / FR-PLUG-06

- **FR-PLUG-01 (no ambient authority).** `wasm-tools component wit` on
  the built `guest-content.component.wasm` shows a component that
  exports `duet:plugin-spike/content-plugin` and imports **nothing** —
  no WASI, no filesystem, no clocks, no network. That's partly an
  artifact of `wasm32-unknown-unknown` having no host ABI to import in
  the first place (see friction note above), but it does concretely
  demonstrate the target property: a guest compiled this way is
  structurally incapable of ambient filesystem/network access — there is
  no import it could call even if the code tried. The real
  implementation still needs the `host` interface (`open-granted`,
  `progress`, `log`, `secret-get` from design.md's sketch) wired through
  explicit, host-mediated imports rather than left off entirely; that's
  T-2.6.1/T-8.1.1 work, not this spike's.
- **FR-PLUG-06 (misbehaving plugin degrades only its own feature).** The
  interruption test is direct evidence for the "infinite loop" case: the
  host thread that called into the guest gets an `Err` back at the
  deadline and keeps running. The spike does not exercise the "panic" or
  "memory blowup" halves of FR-PLUG-06 (panic → instance restart;
  `wasmtime::StoreLimits`/`ResourceLimiter` for the 64MiB memory cap) —
  both are straightforward `wasmtime` features (`Store::limiter`,
  catching the `Result` from `instantiate`/calls around a panicking
  guest) but weren't in this spike's AC and are left to T-8.1.1.

## What this spike did not test

- Multiple concurrent plugin instances / calls (contention on a shared
  `Engine`, pooling allocator behavior).
- Real guest work (EXIF-style parsing) — only the call boundary was
  measured, by design.
- Memory cap enforcement (64MiB default) — not in this AC.
- Fuel-based (vs. epoch-based) interruption — see note above.
- `wasm32-wasip2` end-to-end — blocked by the sandbox's lack of a
  prebuilt wasi-libc; see friction section. Worth retrying on a machine
  with `rustup target add wasm32-wasip2` before committing the project to
  the `wasm32-unknown-unknown` + `wasm-tools component new` path
  long-term.
