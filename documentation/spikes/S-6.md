# S-6 — Text input reality check

**Status:** done (timeboxed spike). **Verdict: proceed, with one confirmed gap and one confirmed unknown.** GPUI on Linux has real, protocol-level IME plumbing (Wayland `zwp_text_input_v3` + X11 XIM + XKB compose), not a stub, and `gpui-component`'s `Input`/`InputState` widget wires all of it up correctly. A 4000-char paste, an emoji/ZWJ/skin-tone/flag paste, and Arabic/Hebrew RTL pastes all round-trip byte-identically with no panic and no layout breakage. But: **`gpui-component` 0.5.1's `Input` does not apply BiDi visual reordering** — RTL text lays out in pure logical (typing) order, which will read backwards to a native Arabic/Hebrew user. And **real CJK IME composition (the actual multi-keystroke candidate-selection flow) could not be exercised at all** — not a tooling limitation of this spike, but a structural one: composition happens in a layer below anything GPUI's own API surface can drive synthetically. See "What genuinely cannot be tested here" below.

## What was built

`spikes/s6-text-input/` — a standalone Cargo project against the same `gpui = "0.2.2"` / `gpui-component = "0.5.1"` pinned in S-1/S-3, pulled straight from crates.io. Two halves:

- **`tests/paste_and_ime.rs`** — five `#[gpui::test]`s driven through `gpui::TestAppContext`, GPUI's own headless test platform (fake window, fake input dispatch, in-process synchronous clipboard). This is the deterministic, reproducible half and the one the verdict above is actually based on. No screen automation, no real display needed — `cargo test` runs it standalone.
- **`src/main.rs`** — a real `Application`, real platform window, opened on this machine's actual Wayland session, self-driving the same four paste scenarios end to end (real OS clipboard, real dispatched `Paste` action, real `cosmic-text` shaping) and printing a report to stdout before calling `cx.quit()`. Kept as the "does this work against the real platform, not just the fake one" half — see the clipboard-race finding below for why it is *not* the reliable oracle.

Both build a single-line `gpui_component::input::Input`/`InputState` (path-bar styled: dark rounded box, `placeholder("Enter a path…")`), the same widget `design.md` §9.5 names for the path bar and inline-rename fields.

### Test cases

| Case | Content |
|---|---|
| 4000-char path | `/home/meir/projects/duet2/spikes/s6-text-input/` + repeated `another-nested-directory-segment-with-numbers-1234567890-and-dashes/` segments, truncated to exactly 4000 bytes |
| Emoji / ZWJ / skin-tone / flag | `📁🗂️👨‍👩‍👧‍👦👍🏽🇺🇸` — folder, card-index-dividers (+ variation selector), a 7-codepoint ZWJ family sequence, a skin-tone-modified thumbs-up, and a 2-codepoint regional-indicator flag: 4 different grapheme-clustering mechanisms in 52 bytes / 5 extended grapheme clusters |
| Arabic RTL path | `/home/meir/مستندات/ملف_مهم_جدا.txt` |
| Hebrew RTL path | `/home/meir/מסמכים/מסמך-חשוב-מאוד.pdf` |

For each, the test: focuses the field, writes the string to the clipboard, dispatches GPUI's real `Paste` action (`gpui_component::input::Paste`, bound to the field's own key context by `input::init`), then asserts:

1. `InputState::value()` after paste is byte-identical to what was written (round-trip correctness, no truncation, no mangling).
2. `marked_text_range()` (the IME preedit/composition range) is `None` afterward — a plain paste must not leave stray composition state.
3. `EntityInputHandler::bounds_for_range` — the same API GPUI uses on Linux to position an IME candidate window — resolves to finite, positive bounds for the whole string, proving layout actually completed without collapsing or panicking on this content.
4. `bounds_for_range` on the first vs. last extended grapheme cluster, compared, to see whether the widget visually reorders RTL content or lays it out in pure logical order.

A fifth test, `ime_marked_text_plumbing_is_live`, bypasses paste entirely and drives `EntityInputHandler::replace_and_mark_text_in_range` → `marked_text_range` → `replace_text_in_range` directly — exactly the sequence GPUI's own Linux platform code calls when a real IME reports a preedit update followed by a commit — to prove the plumbing this widget exposes is live and correct, independent of whether an actual IME engine is attached.

```
test paste_4000_char_path ... ok

test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

Stable across repeated runs (`TestAppContext`'s clipboard is a plain `Mutex<Option<ClipboardItem>>`, synchronous, no real protocol round trip — see `gpui-0.2.2/src/platform/test/platform.rs`).

- **4000-char path: pass.** Round-trips byte-identical; layout produces a sane, finite 33,600px-wide bounding box; no panic, no truncation, no silent clamp.
- **Emoji/ZWJ/skin-tone/flag: pass.** Round-trips byte-identical (52 bytes in, 52 bytes out), so every ZWJ join, variation selector, skin-tone modifier, and regional-indicator pair survived intact — a mangled grapheme cluster would have shown up as a byte-level mismatch, and none did.
- **Arabic and Hebrew RTL: round-trip passes, but layout reveals a real gap.** In both cases the *logically first* grapheme (byte offset 0, the leftmost character when reading the source left-to-right as bytes) is painted at `x=0.0`, and the *logically last* grapheme is painted furthest right. That is **pure logical-order (LTR) layout** — for right-to-left script, a native reader expects the opposite (first-typed character rightmost). `gpui-component` 0.5.1 does not apply BiDi (`unicode-bidi`-style) visual reordering to `Input`'s content; confirmed independently by reading the source (`input/state.rs`, `input/element.rs`, `input/movement.rs` — no `rtl`/`bidi`/`direction` handling anywhere in the crate) and now empirically via `bounds_for_range`.
- **IME marked-text plumbing: pass.** `replace_and_mark_text_in_range(None, "n", None, …)` correctly sets a marked range; a subsequent `replace_text_in_range(None, "你", …)` (simulating an IME commit) correctly replaces it, leaves `value() == "你"`, and clears `marked_text_range()` back to `None`.

## Results — real platform window (`cargo run`), and why it is *not* the oracle

Running the same four scenarios through a real `Application` against this machine's actual Wayland session (`WAYLAND_DISPLAY=wayland-0`) surfaced two genuine, source-confirmed findings that the headless tests above don't hit:

1. **Real clipboard read-after-write is asynchronous, not synchronous.** `App::write_to_clipboard` on Linux calls into `Clipboard::set` (an in-process "what we're offering" cache), but `App::read_from_clipboard` only returns data once the compositor round-trips an actual `wl_data_device` selection *offer* back to the client (`current_offer` in `gpui-0.2.2/src/platform/linux/wayland/clipboard.rs`). Reading immediately after writing, in the same synchronous call, returned `None` every time; polling for a few extra frames let the offer arrive and the paste then succeeded. This is correct Wayland protocol behaviour, not a bug — but it means anything scripting "paste" against a real window needs to tolerate at least one extra round trip.
2. **On a real desktop session, that same read can race with the user's actual system clipboard and return unrelated content.** Across three consecutive runs, one run's "read back what we just wrote" call returned a string that was not ours at all — evidently whatever the host desktop's clipboard already held before the test started. This makes the real-window path fundamentally unsuitable as a deterministic pass/fail oracle (which is exactly why the `TestAppContext` suite above, with its synchronous fake clipboard, is the one this verdict rests on). It is, however, a legitimate reminder that R-G8's real-world paste path shares clipboard state with the rest of the user's desktop and needs to handle "the offer never arrives" / "the offer is something unexpected" gracefully — worth an explicit timeout + fallback in the real path-bar implementation.

Two more integration gotchas turned up building the real-window harness, both worth carrying into `duet-widgets`:

- `Input`'s paint path calls `gpui_component::Root::read`/`Root::update` unconditionally (focus-tracking for its mouse context menu). A window that embeds an `Input` **must** root itself in `gpui_component::Root`, or it panics immediately (`root.rs:268`, `"BUG: window first layer should be a gpui_component::Root"`). Any `duet-widgets` façade around `Input` needs to either document this or wrap it away.
- Calling `InputState::focus()` from inside a closure that already holds a `WindowHandle<Root>::update` borrow panics: `"cannot update gpui_component::root::Root while it is already being updated"`. Focus changes synchronously call back into `Root::update` (to track `Root.focused_input`, used to dismiss menus/autocomplete elsewhere). The fix is to reach `&mut Window` via the App-level `update_window`/`VisualTestContext` path instead of `Entity<Root>::update` — a real re-entrancy trap for anyone driving a `Root`-rooted window programmatically (including a future automated UI test suite for the real app, not just this spike).

## GPUI's IME support — read from source, not guessed

`gpui = "0.2.2"` has a complete, protocol-level `EntityInputHandler` trait (`gpui-0.2.2/src/input.rs`): `text_for_range`, `selected_text_range`, `marked_text_range`, `unmark_text`, `replace_text_in_range`, `replace_and_mark_text_in_range` ("Mark text is the IME temporary insert on typing" — literal doc comment in `gpui-component`'s implementation), `bounds_for_range` (used to position the IME candidate window), and `character_index_for_point`. This is real preedit/composition support, not a paste-only stub.

On Linux specifically, both native input-method protocols are wired up in the platform layer:

- **Wayland**: `gpui-0.2.2/src/platform/linux/wayland/client.rs` binds `zwp_text_input_manager_v3`/`zwp_text_input_v3` (the standard `text-input-unstable-v3` protocol) and handles `Enter`/`Leave`/`CommitString`/`PreeditString`/`Done` events, translated into an internal `ImeInput` enum (`InsertText`/`SetMarkedText`/`UnmarkText`/`DeleteText`, `wayland/window.rs`). `Window::update_ime_position`/`get_ime_area` feed the candidate-window placement back to the compositor.
- **X11**: `gpui-0.2.2/src/platform/linux/x11/xim_handler.rs` implements a full XIM client (`ClientHandler` from the `xim` crate) — `handle_connect`/`handle_open`/`handle_create_ic`, and `XimPreeditEvent`/`XimCommitEvent` callbacks.
- **Dead-key / compose sequences are independent of both of the above.** Both platform clients also hold an `xkbcommon::xkb::compose::State`, built from `xkb::compose::Table::new_from_locale` (`platform/linux/platform.rs::get_xkb_compose_state`), and feed every keysym through it before it reaches the app (`wayland/client.rs` and `x11/client.rs`, both around their key-press handling). This means simple dead-key composition (e.g. `´` + `e` → `é`) is handled by GPUI itself via libxkbcommon's compose tables and **does not require ibus or fcitx to be running at all** — it works purely from the configured X/Wayland keyboard layout's compose file.

`gpui_component::input::InputState` implements `EntityInputHandler` fully and correctly (`gpui-component-0.5.1/src/input/state.rs:1905-2100`): `marked_text_range` is backed by a real `ime_marked_range: Option<Range<usize>>` field, `replace_and_mark_text_in_range` correctly sets/clears it and repositions the selection, and `bounds_for_range` walks the widget's actual last-computed layout (`last_layout`) to return real per-character bounds — not a placeholder. This is the plumbing the `ime_marked_text_plumbing_is_live` test exercises and confirms is live end to end.

## What genuinely cannot be tested here — a documented limitation, not a TBD

**Real CJK IME composition** (typing pinyin/zhuyin/romaji and picking a candidate from ibus's candidate window) could not be exercised, and this is not a gap this spike — or any purely programmatic driver — could close in this environment:

- Composition happens *below* GPUI's own API surface. On Wayland, the compositor routes raw key events to the `zwp_text_input_v3` client (ibus's own input-method implementation), which runs its engine and only then emits `PreeditString`/`CommitString` events back to the application over the protocol. GPUI is a **consumer** of that protocol, not a producer — there is no GPUI API to synthesize "the IME just composed this preedit string," because in the real flow that string is decided by ibus, several process hops away, not by the app.
- `TestAppContext`'s fake platform (`gpui-0.2.2/src/platform/test/window.rs`) implements neither the Wayland text-input protocol nor XIM at all — it has `simulate_keystrokes`/`simulate_input`, which type pre-composed characters directly, bypassing the entire IME layer by construction. Using it to "test IME" would just be testing `replace_text_in_range` again (which `ime_marked_text_plumbing_is_live` already does directly and honestly).
- The only way to genuinely validate this is a human, with ibus actually engaged, typing a real composition sequence into the real running app and confirming the candidate window appears in the right place (`bounds_for_range`/`update_ime_position`, confirmed wired above) and the committed text lands correctly. Per this task's constraints, computer-use/screen automation for newly launched GTK-style windows is broken in this environment, so that human-in-the-loop step could not be performed here either. **This is the one item this spike cannot close**, and it should be carried forward explicitly as a manual acceptance-test step for T-4.3.4 ("IME input works") — not assumed to pass because the protocol plumbing checks out, and not left open-ended.

**Dead keys** are in the same "structurally present, not executed" bucket: the XKB compose code path is confirmed live in GPUI's source (above) and doesn't depend on ibus/fcitx, but exercising it means feeding real X11/Wayland key-press events with a compose-enabled layout through the actual platform client, which — like CJK composition — is not reachable from `TestAppContext` (no compose-table wiring in the fake platform at all) and was not attempted via real synthetic key injection in the real-window harness in this timebox.

## Verdict

**Proceed with GPUI + gpui-component for R-G8**, with two carried-forward items rather than an unqualified pass:

1. **RTL BiDi rendering is a confirmed defect/gap in `gpui-component` 0.5.1's `Input`**, not a hypothesis — empirically demonstrated via `bounds_for_range` in a deterministic test, and consistent with the complete absence of BiDi-related code in the crate's `input` module. Before shipping the path bar or inline-rename against real-world RTL filenames, either (a) file this upstream against `gpui-component` and wait/patch, or (b) have `duet-widgets`' `Input` wrapper apply `unicode-bidi` reordering itself before display (input remains logical-order internally; only the visual presentation needs reordering). Recommend filing upstream now given the timeline, and tracking a `duet-widgets` workaround as the fallback.
2. **CJK IME composition correctness is unverified** and must be a named, human-executed manual test in T-4.3.4's acceptance pass, not inferred from the protocol plumbing being present. The plumbing being real (Wayland text-input-v3 + XIM + XKB compose, all confirmed from source and, for the marked-text/commit half, confirmed live via `ime_marked_text_plumbing_is_live`) is a meaningfully positive signal — this is not a stubbed-out or paste-only text field — but "the pipes exist and are connected" is not the same claim as "composing 你好 with ibus actually works," and this spike cannot make that second claim.

Everything else R-G8 asked about — long paste, emoji/ZWJ/skin-tone grapheme integrity, no panics, no silent truncation, no corruption — is a clean, deterministic, byte-verified pass.
