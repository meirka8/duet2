# S-1 — Virtualised table at scale

**Status:** done (timeboxed spike). **Verdict: proceed, with two flagged risks for G0** (RSS budget vs. framework baseline; per-frame allocation floor set by GPUI internals, not by our data model). Sort AC passes with a one-line mitigation (parallel sort for string-keyed columns). Frame-time AC is **inconclusive on this hardware** — no 120Hz display was available to test against; see below.

## What was built

`spikes/s1-virtualised-table/` — a standalone Cargo binary (not yet part of a workspace; none exists in this repo yet), built against `gpui = "0.2.2"` and `gpui-component = "0.5.1"` pulled straight from crates.io, no vendoring or patches needed.

- `src/store.rs` — `EntryStore`: struct-of-arrays backing data for 1,000,000 rows.
  - Names, and pre-formatted display text for size/date, live in **one** `String` built with a single pre-sized `with_capacity`, then `Box::leak`ed into a `&'static str` arena. Per-row entries are `(u32, u32)` offset/len spans into that arena — one allocation total for a million names, not one per name.
  - `sizes: Vec<u64>`, `dates: Vec<i64>` are raw numeric sort keys, separate from display text, so sorting compares integers, never strings, for those columns.
  - `mode` and `ext` are drawn from small closed vocabularies (6 permission-string variants, 20 extensions) rendered as `&'static str` literals — no arena entry needed at all.
  - `order: Vec<u32>` is the permutation the table actually renders through (`order[display_row] = stable_id`). Sorting only ever rewrites this vector; the SoA arrays underneath never move, matching design.md §9.2.
  - `Bitset` — a flat `Vec<u64>` bitmask indexed by stable row id for multi-selection (not `Vec<bool>`, not tied to display position so it survives re-sorting).
- `src/table_delegate.rs` — `FileTableDelegate: TableDelegate`, over that store:
  - `render_td` returns `SharedString::new_static(&'static str)` for every column — a slice of the arena or a static-table literal. `SharedString` wraps `ArcCow<'static, str>`; `new_static` is `ArcCow::Borrowed`, so this is a genuine zero-allocation, zero-refcount borrow, not even an `Arc` clone.
  - `render_tr` does one `Bitset::get` lookup (by stable id, via `order[row_ix]`) and conditionally sets a background colour for multi-selection highlight — no formatting, no allocation.
  - `perform_sort` permutes `order` in place; column 0 (name) uses `rayon::par_sort_unstable_by` over byte-slice arena comparisons, columns 1–4 use `std::sort_unstable_by_key` over the raw numeric arrays.
  - The keyboard-movable cursor is **not** something we built — `TableState`'s built-in `selected_row` (driven by the existing `SelectUp`/`SelectDown` actions gpui-component already binds to Up/Down) is used directly and gets its highlight rendered by the table itself. We only had to park it once (`set_selected_row(500, …)`) to confirm the code path runs; multi-selection is the part that needed our own bitset because `TableState` only tracks a single `selected_row`/`selected_col`, not a set.
- `src/alloc_track.rs` — a `#[global_allocator]` counting wrapper around `System`, gated by an atomic bool so only the phase under measurement (the scroll loop) is counted; also reads `VmRSS` from `/proc/self/status`.
- `src/main.rs` — orchestrates a fully automated, headless-of-input (but real windowed, real GPU) run: generate data → open window → 30 warm-up frames → 1500 simulated fast-scroll frames (driving `UniformListScrollHandle`'s underlying `ScrollHandle::set_offset` directly by 420px/frame, chained via `Window::on_next_frame`, which is GPUI's "run this after the next frame is presented" hook) → two full-table sorts invoked directly against the delegate (same code path `on_col_head_click` would call) → RSS/alloc report to stdout → `cx.quit()`.

Click-to-sort itself (the actual header-click → `on_col_head_click` → `perform_sort` dispatch) is gpui-component's existing machinery and wired up correctly (`Column::sortable()`); the automated benchmark calls `delegate.perform_sort(..)` directly to avoid needing synthetic mouse input, but it is exactly the same function a real click invokes.

## Environment

- rustc/cargo 1.97.1, Arch Linux, Wayland session (GNOME), NVIDIA RTX 2070 SUPER, proprietary driver, `glxinfo` confirms direct rendering.
- Both `gpui` and `gpui-component` **built cleanly from crates.io on the first real attempt**, no missing system headers, no patched Cargo.toml, no vendoring — this itself is a positive finding against the "might not be buildable" contingency in the task brief.
- **All three connected displays run at ~60Hz** (`xrandr`: 59.88–59.99Hz, no 120Hz mode offered by any output). This matters a lot for the frame-time result below.

## Measured numbers

Four full runs were taken; numbers were stable run-to-run (±10%). Representative run:

```
RSS after Application::new()+gpui_component::init (framework baseline, no data, no window): 248,328 kB
Generation done in 349ms, ~82.8 MB accountable SoA+arena bytes
RSS after data generation:        335,436 kB
RSS after first paint (warm):     362,176 kB
RSS after scroll benchmark:       362,824 kB
RSS after sort benchmark:         363,408 kB

-- scroll frame time (1499 samples) --
  p50: 16.67 ms   p99: 43.2 ms   max: 79.4 ms   mean: 17.3 ms
  frames over 8.3ms: 1499 / 1499 (100%)

-- allocator activity during 1500 scroll frames --
  alloc events:   14,674,102  (≈ 9,783 / frame)
  alloc bytes:    5,213,052,225  (≈ 3.5 MB / frame, fully offset by matching deallocs — flat RSS)
  dealloc events: 14,673,187
  realloc events: 3,175,688

-- sort of 1,000,000 rows --
  size (u64 key, std::sort_unstable_by_key):        ~73–76 ms
  name (byte-slice key, std single-threaded):        ~500–670 ms   (OVER the 400ms AC)
  name (byte-slice key, rayon par_sort_unstable_by): ~199–201 ms   (under, after a ~10-line change)
```

`GPUI_MEASUREMENTS=1` (gpui-component's own built-in per-cell timer, `src/table/state.rs::measure_render_td`) gave, for every sampled frame during scroll: **~128–134 cells rendered, total ~50–67µs, average ~390–500ns/cell** — i.e. the part of the pipeline our `TableDelegate` controls costs well under 0.1ms per frame, ~0.6–0.8% of an 8.3ms budget.

## Acceptance criteria — verdicts

### 1. Frame time under 8.3ms while scrolling at speed — **inconclusive on this hardware**

The raw number (p50 16.67ms, 100% of frames "over budget") looks like a hard fail, but it's confounded by the test environment, not by the table: `Window::on_next_frame` fires once per *presented* frame, gated by the compositor's vsync/frame-callback. With every display here locked at ~59.9Hz, the measured inter-frame interval cannot go below ~16.7ms **no matter how fast the render code is** — that floor is a property of this machine's display hardware, not of Duet's code. p50 landing almost exactly on 16.67ms (1/60s) is the signature of "hitting vsync every single frame, no drops," which is actually the *good* outcome at 60Hz.

What we can say with the instruments available:
- The decoupled per-cell render cost (GPUI's own instrumentation, not vsync-gated) is ~60µs/frame for the full visible grid — two orders of magnitude under an 8.3ms budget. Nothing about how the delegate touches SoA data is a bottleneck.
- p99 (37–46ms) and max (49–79ms) sit at roughly 2–5× the single-vsync floor, which does indicate real occasional stalls beyond simple vsync pacing (likely layout re-flow or cosmic-text glyph-cache misses as new rows scroll into view for the first time) — this is a genuine signal worth re-testing on real 120Hz hardware, not an artifact.
- **This AC cannot be honestly validated without a 120Hz-capable display + compositor.** Recommend re-running this exact spike binary on such hardware before treating frame time as settled at G0.

### 2. Sort of 1M rows under 400ms — **pass, with a one-line mitigation**

Numeric-keyed columns (size/date/mode/ext) sort in ~75ms with plain `std::sort_unstable_by_key` — comfortable pass. The string-keyed column (name) is the expensive case: single-threaded byte-slice comparison sort took 500–670ms, over budget. Switching just that column to `rayon::slice::ParallelSliceMut::par_sort_unstable_by` (24 cores available in this environment) brought it to ~200ms consistently. Cheap, low-risk, and exactly the kind of per-column tuning `EntryStore::sort_by_column` was designed to allow. **Recommend `duet-index`'s real sort implementation default to a parallel sort for any string/locale-collated key from the start.**

### 3. RSS under 300MB — **fails as measured, but the SoA design is not the cause**

Steady-state RSS after load + 1500 scroll frames + two full sorts: ~363MB, over budget. But: `Application::new()` + `gpui_component::init()` alone — **before any of our data and before opening a window** — already sits at ~248MB RSS (font enumeration via cosmic-text, theme registry, Wayland platform setup). Our 1,000,000-row SoA data + window + first paint adds only ~114MB on top of that (248MB → 362MB), and critically **does not grow further** during scrolling (362.1 → 362.8MB over 1500 simulated frames, +0.6MB) or after a full-table sort (362.8 → 363.4MB) — no leak, no per-scroll growth. The `EntryStore`'s own accountable footprint is ~83MB for 1M rows (arena + parallel arrays), matching the design's SoA byte-budget intent.

Read plainly: the data model is memory-disciplined and would fit the 300MB budget with room to spare on its own. The AC fails because gpui-component 0.5.1's own startup baseline (~248MB) leaves under 52MB of headroom for an entire application. **This is a framework-level finding, not a table-design finding** — it should go to G0 as an open question: does NFR-06's 300MB target assume a lean process baseline that gpui-component doesn't currently deliver, and if so is that fixable (deferred font enumeration, lazy theme loading) or a hard ceiling to design around?

### 4. TableDelegate/SoA fit — **the API shape does not force per-row allocation; the surrounding framework is not allocation-free regardless**

Both halves of this are load-bearing and neither should be dropped from the record:

- **The delegate API genuinely fits SoA.** `render_td(row_ix, col_ix, …) -> impl IntoElement` and `render_tr(row_ix, …) -> Stateful<Div>` take indices, not owned data, and place no requirement on what you return. A SoA-backed delegate can return `SharedString::new_static(&'static str)` — a zero-allocation, zero-refcount borrow into a pre-built arena — for every cell, and a bitset lookup for selection highlighting, with **zero heap allocation in the delegate's own code**. This was verified two ways: by construction (code review — no `format!`, `String::from`, or `Vec<bool>` anywhere in `table_delegate.rs`) and empirically (GPUI's own per-cell timer shows ~400ns/cell, consistent with "borrow + a couple of style calls," not string formatting).
- **The literal, whole-process "zero allocations while scrolling" claim does not hold with gpui-component 0.5.1 as shipped.** The counting global allocator shows ~9,700–9,900 allocation events per rendered frame (matched by an equal number of deallocations — steady, not leaking) even though the delegate itself allocates nothing. That volume, at ~134 visible cells/frame, is roughly 70 alloc events per visible cell — almost certainly from GPUI/gpui-component's own per-frame machinery: boxed `on_click`/`on_mouse_down` listener closures created fresh per row every frame (`render_table_row` does this unconditionally), Taffy layout node bookkeeping, cosmic-text glyph shaping, and `Vec::with_capacity` calls inside `uniform_list`/`virtual_list`'s row/column iteration. Root-causing the exact call sites (heaptrack/valgrind massif) was out of scope for this time-box — `heaptrack` isn't installed in this environment and a full massif run against a windowed GPU app wasn't attempted given the 4-day budget — so this is flagged, not fully diagnosed.
- Whether that per-frame churn actually threatens an 8.3ms budget on real 120Hz hardware is **unresolved**: 3.5MB/frame of alloc/dealloc churn is well within what a modern allocator handles in well under a millisecond in isolation, so this reads more as a GC-pressure/code-quality risk than a proven latency blocker — but it deserves a follow-up measurement once a 120Hz display is available, ideally with `heaptrack` or similar to attribute the allocations.

## Net read for G0

Proceed with GPUI + gpui-component, per ADR-001. Nothing here reproduces the "delegate API forces per-row allocation" failure mode the kill criteria in task.md worry about — the opposite was demonstrated: a from-scratch SoA delegate is allocation-free by construction. The two real open items are (a) validate frame time on genuine 120Hz hardware before calling NFR-05 settled — this environment structurally cannot test it, and (b) treat gpui-component's ~248MB startup baseline and its ~9,800 allocs/frame internal churn as tracked risks for T-4.2.1, not blockers to starting.

## Reproducing

```
cd spikes/s1-virtualised-table
cargo build --release
WAYLAND_DISPLAY=wayland-0 DISPLAY=:0 ./target/release/s1_virtualised_table
# add GPUI_MEASUREMENTS=1 to also get gpui-component's own per-cell render timing on stderr
```
The binary is fully self-driving (simulates its own scroll and sort, no interaction needed) and exits automatically after printing its report.
