# S-5 — Copy strategy ladder (Phase 0 spike)

**Question this spike answers:** what's the fastest correct way to copy files on Linux, and is `io_uring` worth adopting for 1.0?

**Cross-references:** FR-OPS-06, NFR-07, T-5.1.4, T-9.3.5 (design.md §9.3: "`io_uring` batching for many small files — feature-gated, benchmarked in Phase 9, adopted only if it wins by >15%").

**Status:** complete, timeboxed (3-day budget per task.md). Headless, non-UI micro-benchmark harness; not production code.

**Code:** `spikes/s5-copy-ladder/` (standalone Cargo project, `rustix` for raw syscalls per design.md §7.5, `io-uring` crate for the io_uring ladder rung). Run with `cargo run --release -- run --root <dir> [--large-mib N] [--small-count N]` or `... probe --root <dir>` for a quick capability check.

## TL;DR

- **On the reflink-capable disk tested (btrfs/NVMe), `ficlone`, `copy_file_range`, and coreutils `cp`/`cp -a` are all statistically free (~0.2-1.7 ms) for a 2 GiB file**, because btrfs's `copy_file_range` implementation opportunistically reflinks, and GNU coreutils' `cp` already tries `copy_file_range`/`FICLONE` before falling back to read/write. A real (non-reflink) buffered copy on the same disk runs 230-350 MiB/s.
- **On ext4 (no reflink, confirmed via a negative-case probe: `ioctl(FICLONE)` → `EOPNOTSUPP`), `cp` and `copy_file_range` are again statistically identical (~3.3-3.4 GiB/s)** because coreutils `cp` uses `copy_file_range` internally; naive buffered copy is 20-30x slower on that path.
- **`posix_fadvise(DONTNEED)` reliably suppresses page-cache growth by 25-180x for a large single-file copy** (from ~2.0-2.1 GB of `Cached` growth down to 11-80 MB) with a throughput cost that was inconsistent in sign across runs (neutral to mildly negative) — i.e. it does what it's for, at low and noisy cost.
- **Per-file `fsync` is catastrophic for many-small-files throughput**: 50,000 files went from ~22,700 files/s (no fsync) to ~210 files/s (fsync every file) — a ~108x regression. This is the real cost of "durable per file" semantics and belongs in the FR-OPS-07 journal design as an explicit, deliberate trade-off, not a default.
- **`io_uring` batching, as implemented here (batched-submission, not linked/fixed-file chains), did not win on the many-small-files corpus.** It ran at ~16,100 files/s vs. ~25,000-25,600 files/s for a plain per-file `ficlone`/`copy_file_range` loop — a **loss**, not the >15% win design.md §9.3 requires for adoption.
- **Go/no-go: no-go on `io_uring` for 1.0.** See "io_uring go/no-go" below for the full reasoning and what would change the answer.

**Important:** the btrfs and ext4 numbers below are **not** a clean filesystem-vs-filesystem comparison — they ran on different physical media (NVMe SSD vs. spinning HDD). Comparisons within a filesystem/disk (the ladder run on btrfs against itself, or on ext4 against itself) are apples-to-apples; the ext4 run exists mainly to (a) generate a real `FICLONE`-unsupported negative case and (b) show `cp`/`copy_file_range`'s relative behavior on a filesystem that can't take the reflink shortcut.

## Corpora

- **Large file**: 2048 MiB (2 GiB) of pseudo-random bytes (not sparse, not trivially compressible), regenerated fresh for each full run.
- **Many small files**: 50,000 files, 1-8 KiB each (uniform), ~220-230 MB total, flat directory.
- Both corpora were generated under a scratch directory outside the repo, benchmarked, verified, and deleted at the end of each run; nothing was committed. `spikes/s5-copy-ladder/.gitignore` excludes `/target` and any stray `*.json` result dumps.

## Results: large file (2 GiB), btrfs on NVMe SSD

Two independent full runs (`run2`, `run3` below) to sanity-check variance:

| strategy | run2 | run3 | cache Δ (run2 / run3, kB) |
|---|---:|---:|---:|
| `ficlone` | 0.2 ms (unmeasurably fast) | 0.2 ms | 0 / 0 |
| `copy_file_range` | 0.2 ms | 0.2 ms | 0 / 0 |
| `buffered_1mib` | 228.8 MiB/s | 344.3 MiB/s | +1,893,420 / +2,097,648 |
| `buffered_4mib` | 242.3 MiB/s | 349.6 MiB/s | +2,107,540 / +2,096,752 |
| `buffered_4mib_fadvise` | 125.8 MiB/s | 335.0 MiB/s | **+11,364** / **-300** |
| `cp` | 1198,497 MiB/s (reflink fast path) | 1213,424 MiB/s | 0 / 0 |
| `cp_a` | 1173,293 MiB/s | 1559,726 MiB/s | 0 / 0 |

Reading this table correctly matters: `ficlone`, `copy_file_range`, `cp`, and `cp_a` are not "infinitely fast" copies of 2 GiB of data — they're **metadata-only copy-on-write reflink operations**. btrfs's `copy_file_range` syscall implementation opportunistically clones extents when it can, and GNU coreutils' `cp`/`cp -a` already try `copy_file_range`/`FICLONE` before falling back to a read/write loop, so on a reflink-capable filesystem all four converge to "effectively free." The only strategies actually moving 2 GiB of bytes through the page cache here are the three `buffered_*` rows, which land in the 230-350 MiB/s range (run-to-run variance is real desktop-noise variance, not a bug — see "Limitations").

## Methodology corrections made mid-spike

Two numbers in the first full run were wrong and worth stating plainly, because the wrong numbers would have driven the wrong conclusion:

1. **`copy_buffered` unconditionally called `fsync` on every file.** For the large-file corpus that's one fsync total (negligible). For the 50,000-small-file corpus it meant 50,000 fsyncs, which dominated the measurement — the first run showed "buffered copy" as ~140x slower than `ficlone`, which conflated "buffered I/O is slow" with "fsync-per-file is slow." Fixed by adding an explicit `fsync: bool` parameter and splitting it into its own labeled row (`buffered_256kib_fsync`) so the fsync cost is visible on its own rather than hidden inside every buffered measurement. This is now a first-class finding, not a bug: **it directly quantifies what FR-OPS-07's crash-safety guarantees would cost if implemented as "fsync every file."**
2. **The `io_uring` batching implementation used a 1 MiB per-slot buffer for files that are 1-8 KiB.** With 256 files in flight per batch, that's 256 MiB allocated and zeroed per batch (~196 batches for 50k files, ~50 GB of memset total) to move ~230 MB of actual payload — a self-inflicted 1000x overallocation that swamped everything else and made the first `io_uring` run look catastrophically slow (33.7 MiB/s). Fixed by sizing the buffer to 64 KiB (8x headroom over the corpus's 8 KiB ceiling) — a fix that should have been obvious from the corpus spec but wasn't caught until the numbers looked implausible. After the fix, `io_uring` still lost to `ficlone`/`copy_file_range` (see table above), but by a believable ~1.6x margin rather than a fabricated ~2.4x-from-a-bug margin.

Both are logged here rather than silently corrected because they're exactly the kind of mistake a production copy-engine implementation could also make, and both point at real design constraints (don't fsync-per-file by default; size io_uring buffers from real data, not round numbers).

## Page-cache eviction findings

`vmtouch` is not installed in this environment and is not in the distro's official repos (only checked, not installed — installing a system package was treated as out of scope for a headless benchmark spike). Per the task's documented fallback, `/proc/meminfo`'s `Cached:` field was sampled immediately before and after each strategy call as a proxy.

**This proxy is honest but noisy** — it's a system-wide counter on a real, otherwise-in-use desktop, not a per-file residency check. Two things make the large-file result trustworthy despite that:

- The effect size is enormous and consistent in both independent runs: buffered copy **without** fadvise grows `Cached` by ~2.0-2.1 GB (essentially the whole file, both read and write side); buffered copy **with** `POSIX_FADV_DONTNEED` on the source behind the read cursor grows it by only 11-80 MB — a 25x to 185x reduction, reproduced twice.
- `ficlone`/`copy_file_range`/`cp`/`cp -a` show ~0 cache delta, consistent with them being CoW metadata operations that never bulk-move data through the page cache — exactly what should happen.

The many-small-files cache deltas are noisier (some even negative, e.g. `copy_file_range: -3,544 kB`) because that phase runs for several seconds and any concurrent system activity on this shared desktop shows up in a system-wide counter; **read those numbers as directional, not precise**. The one clean small-file signal: fadvise's effect on small files is much smaller than on the large file (it doesn't reliably show the same order-of-magnitude suppression), which makes sense — `POSIX_FADV_DONTNEED` is a per-file-region hint, and there's very little to evict behind the cursor of a 4 KB read. **Recommendation: gate `fadvise(DONTNEED)` on transfer size** (e.g. only apply it once cumulative bytes read for a job exceed some threshold, not per 1-8 KiB file), which also sidesteps the extra syscall cost fadvise adds per tiny file.

**If this becomes a release gate rather than a spike finding, install `vmtouch` (or use `/proc/[pid]/smaps` / `mincore(2)` directly) for a real per-file residency check** — the meminfo proxy was good enough to confirm the direction and rough magnitude of the effect, not to certify it.

## io_uring go/no-go

**No-go for 1.0.**

design.md §9.3 sets the bar explicitly: io_uring batching for many small files is "adopted only if it wins by >15%" over the existing ladder. This spike's implementation — batched (not linked/chained) submission of `OpenAt`/`Read`/`Write`/`Close` in phases of 256 files per `io_uring_enter` round-trip — measured **~16,130 files/s against ~25,150-25,560 files/s for a plain synchronous `ficlone`/`copy_file_range` loop**: a loss of roughly 35-40%, not a win of 15%.

Why it lost, honestly:

- `ficlone`/`copy_file_range` on this corpus benefit from the same reflink/kernel-side-copy shortcut that made the large-file numbers look "free" — for tiny files that's still a single syscall each, essentially as cheap as an `io_uring_enter` round-trip amortized over a batch, so io_uring's main lever (fewer syscalls) has very little headroom to win against an already-single-syscall-per-file baseline.
- This implementation does not use registered/fixed file descriptors or linked SQE chains — each file still costs open+read+write+close (4 ops), just submitted in batches rather than issued as 4 separate blocking syscalls. That removes syscall *dispatch* overhead but not *op count*, and per-batch bookkeeping (buffer pool, two extra full submit+wait round trips versus a naive loop's single pass) adds its own cost.
- A more aggressive implementation (fixed-file direct descriptors, `IOSQE_IO_LINK` chains so open→read→write→close execute server-side without a userspace round-trip between them, `IORING_SETUP_SQPOLL` to avoid `io_uring_enter` on the hot path entirely) could plausibly close or reverse this gap. That's real, uninvested engineering effort, not a settled loss for io_uring as a technology — it's a loss for the ROI of building that engineering effort **for 1.0**, on a corpus where the non-io_uring baseline (reflink/copy_file_range) is already this fast.

**Recommendation:** do not build the io_uring rung for 1.0. Keep `duet-ops`'s copy ladder at `ficlone → copy_file_range → buffered(+fadvise)` per FR-OPS-06/design.md §9.3 items 1-3. Revisit io_uring post-1.0 if/when there's a concrete workload where reflink/`copy_file_range` *aren't* available (e.g. cross-filesystem many-small-files moves, or a filesystem without reflink) — that's the scenario where io_uring's batching has the most headroom to show a real win, and it wasn't the scenario this spike's corpus tested (both benchmark disks support `copy_file_range`, even where reflink doesn't apply).

## Cross-reference: NFR-07 and FR-OPS-06

- **NFR-07** ("≥95% of `cp` for large files; ≥80% of `cp -a` for 100k small files, measured against coreutils on the same disk"): on a reflink-capable filesystem, `cp` itself is essentially free (it takes the same `copy_file_range`/`FICLONE` shortcut), so **the only way `duet-ops` hits 95% of `cp` on such a filesystem is to also attempt reflink first** — exactly the ladder order FR-OPS-06 and design.md §9.3 already specify (`FICLONE` → `copy_file_range` → buffered). A copy engine that skipped straight to buffered I/O would land at roughly 230-350 MiB/s against a `cp` baseline of >1,000,000 MiB/s on this disk — nowhere close to 95%. The NFR is trivially satisfiable *only* by implementing the ladder as designed, which is a useful confirmation that the ladder ordering is load-bearing, not a nice-to-have.
- On ext4 (no reflink), the ladder still needs `copy_file_range` specifically (not just buffered) to have a chance at 95% of `cp`, since `cp` gets its speed from `copy_file_range` there too — a plain buffered fallback was 20-30x slower than `cp` on that disk.
- **FR-OPS-06** ("same-filesystem copies attempt reflink then `copy_file_range` then buffered fallback"): confirmed as the right ladder order by this spike — reflink is free when available, `copy_file_range` is the correct next fallback (fast even without reflink, per the ext4 numbers), and buffered is correctly last resort.
- The many-small-files 80%-of-`cp -a` bar is comfortably clear for `ficlone`/`copy_file_range`/plain-buffered (~92-124% of the `cp -a` figure measured here, run-to-run), but is **not** clear for the fsync'd-per-file variant (~1% of `cp -a`) — reinforcing that per-file fsync must be an explicit, non-default choice in the journal design, not baked into the default copy path.

## Limitations of this spike

- Single-machine, single-session measurements; no statistical repeats beyond the 2-3 runs shown, on a shared desktop with other processes running (visible in some of the noisier cache-delta and large-file-throughput numbers). Treat magnitudes as indicative, not lab-grade.
- `/proc/meminfo` `Cached:` is a system-wide proxy, not a per-file residency check (`vmtouch` unavailable, not installed — see above).
- The ext4 disk is a spinning HDD, not an SSD; its buffered-copy numbers reflect that physical difference as much as the filesystem, and should not be read as "ext4 is slower than btrfs."
- The io_uring implementation tested is a batched-submission design, not the more aggressive linked-chain/fixed-descriptor/SQPOLL design that would represent io_uring's real ceiling; the go/no-go call is about ROI for 1.0 given that gap, not a claim that io_uring cannot ever win here.
- Corpus sizes (2 GiB large file, 50k small files) were chosen to fit comfortably within available disk headroom (41 GiB free on the btrfs test disk) rather than matching NFR-07's 100k-small-files / much-larger-file wording exactly; the relative rankings between strategies are expected to hold at the larger scale, but absolute throughput numbers at 100k files / larger file sizes were not independently confirmed here.
