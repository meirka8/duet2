# S-2 — Clipboard with custom MIME types

**Status: GREEN, with a costed workaround.** GPUI's clipboard API does **not**
suffice — this is a structural gap, not a missing convenience wrapper — but a
working Wayland-fallback prototype exists, is self-verified end to end, and
the integration cost is well inside the ~10-day kill-criteria threshold in
`task.md`.

Traces: FR-CFG-05, R-G2, OQ-1.

## Environment note: no interactive Nautilus/Dolphin testing

Per instructions for this spike, interactive GUI testing was skipped:
computer-use/screen automation is confirmed broken for newly-launched GTK
windows in this environment (Nautilus and even `gnome-calculator` never
render, despite running as live processes). All verification below is done
at the OS/Wayland-protocol level via CLI-driven, non-interactive tooling
built specifically for this purpose — which is also, not incidentally, a
stronger proof of the actual thing S-2 needs to prove (does the byte-level
clipboard exchange work) than driving one specific app's UI would be.

The session is a real GNOME/mutter Wayland session (`gnome-shell --mode=user`,
`XDG_SESSION_TYPE=wayland`), not headless/nested, so the protocol-level
behavior observed here (keyboard focus assignment, selection delivery) is the
same behavior Nautilus/Dolphin would see.

## 1. Does GPUI's clipboard API support custom MIME types?

Investigated by reading the actual crate source for `gpui = "0.2.2"` (same
version pinned by the S-1 spike), fetched into
`~/.cargo/registry/src/index.crates.io-*/gpui-0.2.2/`. No guessing.

**No, at two independent levels:**

**a) The public type cannot express it.** `gpui::ClipboardItem` wraps
`Vec<ClipboardEntry>` (`src/platform.rs:1510`), and `ClipboardEntry` has
exactly two variants:

```rust
pub enum ClipboardEntry {
    String(ClipboardString),
    Image(Image),
}
```

There is no `Custom`/`Mime`/`Raw` variant. `App::write_to_clipboard(item:
ClipboardItem)` / `App::read_from_clipboard() -> Option<ClipboardItem>`
(`src/app.rs:1041,1053`) are the entire public surface. It is not possible to
ask GPUI to put `text/uri-list` or any other MIME type on the clipboard
through this type at all, regardless of platform.

**b) The Linux/Wayland backend hard-codes plain text.**
`src/platform/linux/wayland/clipboard.rs` defines:

```rust
pub(crate) const TEXT_MIME_TYPES: [&str; 3] =
    ["text/plain;charset=utf-8", "UTF8_STRING", "text/plain"];
pub(crate) const FILE_LIST_MIME_TYPE: &str = "text/uri-list";
pub(crate) const ALLOWED_TEXT_MIME_TYPES: [&str; 2] =
    ["text/plain;charset=utf-8", "UTF8_STRING"];
```

- **Writing:** `wayland/client.rs:833-838` — when GPUI takes the selection, it
  offers *only* `TEXT_MIME_TYPES` plus an internal `self_mime` sentinel to the
  compositor. `Clipboard::send()` (`clipboard.rs:182-186`) ignores the
  requested MIME type entirely and always sends `contents.text()` bytes if
  present — there is no code path that could ever serve `text/uri-list` or
  `x-special/gnome-copied-files` from the clipboard, because nothing ever
  offers them for the clipboard selection in the first place.
- **Reading:** `Clipboard::read()` (`clipboard.rs:198-214`) tries
  `read_text()` (only `ALLOWED_TEXT_MIME_TYPES`) then `read_image()`. It never
  looks at `text/uri-list` or any GNOME/KDE marker.
- `FILE_LIST_MIME_TYPE` **does** appear in `wayland/client.rs`, but only in
  the `wl_data_device::Event::Enter` handler (`client.rs:1896-1966`) — that is
  the **drag-and-drop** code path (`PlatformInput::FileDrop`), a completely
  separate mechanism from copy/paste. It is never wired into
  `Clipboard::read`/`send`.

**Conclusion:** GPUI's clipboard API is structurally incapable of carrying
`text/uri-list`, `x-special/gnome-copied-files`, or
`application/x-kde-cutselection`, at both the type-system level and the
Wayland-backend implementation level. No amount of call-site cleverness
against the current public API fixes this; it would require upstream changes
to GPUI itself. This spike therefore proceeds to the Wayland fallback named
in the AC.

## 2. What was built

`spikes/s2-clipboard/` — a standalone Cargo project (`gpui` is *not* a
dependency of it; the investigation above didn't require compiling gpui,
only reading its source, given how conclusive the type-level finding is).
Dependencies: `smithay-client-toolkit = "0.21.1"` (feature `calloop`),
`wayland-client = "0.31.15"`, `wayland-protocols = "0.32.13"` — versions
resolved and locked by Cargo, matching what SCTK 0.21.1 itself uses.

Binary `s2_clipboard`, three subcommands:

- **`write-copy` / `write-cut`** — creates fixture files
  `/tmp/duet-s2-test/{a,b}.txt` if missing, connects to the compositor, and
  creates a tiny (16×16, offscreen-in-practice) `xdg_toplevel` surface. This
  surface exists for exactly one purpose: to receive keyboard focus, because
  `wl_data_device.set_selection` requires a serial, and the **only** valid
  source of that serial is a recent input-event serial for a surface this
  client owns (this is also why `wl-copy` from `wl-clipboard` creates a
  surface — it is not optional). On `wl_keyboard::enter`, it immediately uses
  that serial to create a `CopyPasteSource` offering:
  - copy: `text/uri-list`, `x-special/gnome-copied-files`
  - cut: `text/uri-list`, `x-special/gnome-copied-files`,
    `application/x-kde-cutselection`

  and calls `set_selection`. It then blocks on its event loop, serving
  `send_request` (mime-specific payload write) events indefinitely — it must
  stay alive as the clipboard owner, because Wayland has no central clipboard
  manager; if this process dies, the selection is gone (same lifetime
  contract `wl-copy` has, and the same reason it normally daemonizes).
  Payload formats (`src/mime.rs`) match design.md §9.10 exactly, e.g.
  `x-special/gnome-copied-files` = `"cut\nfile:///tmp/duet-s2-test/a.txt\nfile:///tmp/duet-s2-test/b.txt\n"`.

- **`read`** — reads back whatever the current selection owner offers. This
  needed its own focus-grabbing surface too, which was **not** anticipated
  going in and cost real debugging time to discover: `wayland.xml` states
  outright, for `wl_data_device.selection`, "*The selection event is sent to
  a client immediately before receiving keyboard focus and when a new
  selection is set while the client has keyboard focus.*" A window-less
  client that only creates a `wl_data_device` — which is what a first cut of
  `read` did — never receives the offer at all, no matter how long it waits,
  even though a selection genuinely exists. `read` now creates the same kind
  of minimal surface as `write-*`, and treats `wl_keyboard::enter` as the
  trigger that the current selection offer (if any) has just arrived. It then
  prints every offered MIME type and, for the ones we care about
  (`text/uri-list`, `x-special/gnome-copied-files`,
  `application/x-kde-cutselection`, plus plain-text variants as a fallback
  for eyeballing what other apps put on the clipboard), the decoded content.

  A second bug found and fixed during development: `SelectionOffer::receive()`
  returns a pipe you must **not** read from blocking-style before flushing
  the Wayland connection (documented in SCTK's own doc comment, easy to miss)
  — the `wl_data_offer.receive` request has to actually reach the compositor
  and get relayed to the source client as `wl_data_source.send` before
  anything will ever be written into the pipe. The first version deadlocked
  forever on `read_to_end()`. Fixed by queuing all `receive()` calls for the
  interesting MIME types, calling `conn.flush()` once, and only then doing
  the blocking reads.

## 3. Self-verification (no GUI interaction, two separate process invocations)

`write-copy`/`write-cut` and `read` were run as genuinely separate OS
processes — `write-copy` backgrounded and kept alive, `read` invoked
afterward as its own process — which is the actual round trip S-2 needs to
prove (one process/app puts data on the system clipboard, a different one
reads it back through the compositor, not through shared in-process state).

**Copy:**

```
$ s2_clipboard write-copy &
[s2-clipboard write-copy] fixtures: ["file:///tmp/duet-s2-test/a.txt", "file:///tmp/duet-s2-test/b.txt"]
[s2-clipboard write-copy] waiting for keyboard focus to obtain a serial...
[s2-clipboard write-copy] got keyboard focus (serial=7207)
[s2-clipboard write-copy] creating data source, offering mime types: ["text/uri-list", "x-special/gnome-copied-files"] (serial=7207)
[s2-clipboard write-copy] selection set. Serving clipboard requests (this process must stay alive -- kill it when done verifying).

$ s2_clipboard read     # separate process
read: got keyboard focus (serial=7213) -- selection offer should have just arrived
read: mime types offered: ["x-special/gnome-copied-files", "text/uri-list"]
read: [x-special/gnome-copied-files] (67 bytes) = "copy\nfile:///tmp/duet-s2-test/a.txt\nfile:///tmp/duet-s2-test/b.txt\n"
read: [text/uri-list] (62 bytes) = "file:///tmp/duet-s2-test/a.txt\nfile:///tmp/duet-s2-test/b.txt\n"
```

**Cut:**

```
$ s2_clipboard write-cut &
[s2-clipboard write-cut] got keyboard focus (serial=7141)
[s2-clipboard write-cut] creating data source, offering mime types: ["text/uri-list", "x-special/gnome-copied-files", "application/x-kde-cutselection"] (serial=7141)
[s2-clipboard write-cut] selection set. Serving clipboard requests (this process must stay alive -- kill it when done verifying).

$ s2_clipboard read     # separate process
read: mime types offered: ["application/x-kde-cutselection", "x-special/gnome-copied-files", "text/uri-list"]
read: [application/x-kde-cutselection] (1 bytes) = "1"
read: [x-special/gnome-copied-files] (66 bytes) = "cut\nfile:///tmp/duet-s2-test/a.txt\nfile:///tmp/duet-s2-test/b.txt\n"
read: [text/uri-list] (62 bytes) = "file:///tmp/duet-s2-test/a.txt\nfile:///tmp/duet-s2-test/b.txt\n"
```

**Negative check** (selection correctly cleared, not stale/cached data): after
killing the `write-cut` process, a subsequent `read` correctly reports no
offer rather than replaying old content:

```
$ kill <write-cut pid>
$ s2_clipboard read
read: no clipboard selection offer observed within 10s (clipboard may be empty, we never got keyboard focus, or no seat/data-device-manager present).
```

Both `cargo build` (debug) and `cargo build --release` were exercised; the
release binary reproduces the identical copy round trip.

## 4. Independent cross-check (wl-copy/xclip) — gap, no sudo

`which wl-copy wl-paste xclip xsel` all report "not found" on this system;
`pacman -Qs` confirms none of `wl-clipboard`, `xclip` are installed. No sudo
is available in this environment and none was used. **This independent
cross-check could not be performed** — noted as a gap per the task
instructions, rather than skipped silently.

Mitigating factors for why §3 is still strong evidence:
- `write-*` and `read` are separate OS processes with independent Wayland
  connections and independently-implemented protocol object graphs (no
  shared state, no shared code path for encoding vs. decoding beyond the
  small `mime.rs` payload-format helpers) — this is a materially stronger
  test than an in-process round trip would be.
- The payload bytes read back match design.md §9.10's documented format
  exactly, byte for byte, including the GNOME `copy`/`cut` verb prefix and
  the KDE `"1"` cut marker.
- The behavior discovered along the way (selection delivery gated on
  keyboard focus; the receive-then-flush ordering requirement) matches
  documented Wayland core protocol semantics (`wayland.xml`) and SCTK's own
  doc comments, not just this tool's self-consistency — i.e., the mechanism
  understood here is the *general* mechanism any compositor-conformant
  client (including Nautilus/Dolphin) uses, not something specific to this
  spike's code.

## 5. Verdict

**GPUI's clipboard API does not suffice** — confirmed by direct source
inspection at both the type level (`ClipboardEntry` has no custom-MIME
variant) and the Linux/Wayland backend level (only ever offers/reads
plain-text MIME types for the clipboard selection; `text/uri-list` exists in
that file only for the unrelated drag-and-drop path).

**The Wayland fallback works.** A working prototype using `wl_data_device`
directly via `smithay-client-toolkit`, run alongside (not through) GPUI,
successfully writes and reads `text/uri-list`, `x-special/gnome-copied-files`,
and `application/x-kde-cutselection` across independent process boundaries,
self-verified end to end for both copy and cut semantics.

**Integration cost estimate: ~5–7 engineer-days** for production integration
into `duet-platform`/`duet-ui`, comfortably under the ~10-day kill-criteria
threshold in `task.md`'s Phase 0 gate. Breakdown:

| Item | Est. |
|---|---|
| Wire SCTK/wayland-client into the real app; bridge its calloop event loop with GPUI's own executor/event loop (thread or shared-loop integration) | 1 d |
| Production write path: real copy/cut UI action → live panel selection → `set_selection`; correct handling of re-copying (destroying/replacing the previous `CopyPasteSource`), `Cancelled` events | 1 d |
| Production read path (paste action): mime negotiation preferring `text/uri-list`, falling back to plain text for interop with apps that only copy text; likely **reuses the app's own already-focused window/keyboard** instead of a second ephemeral surface (a simplification this spike's throwaway CLI tool couldn't take advantage of, since it has no real window of its own) | 1 d |
| Cut-state UX: dimmed/marked cut files in the panel, clearing cut state on paste-elsewhere or on a new copy/cut superseding it, matching Nautilus/Dolphin conventions | 0.5–1 d |
| X11 fallback via `x11rb` selections (ICCCM/`INCR` for large transfers) for non-Wayland sessions — a materially different code path from the Wayland one; **not attempted in this spike**, since this environment is Wayland-only, and is the largest open item below | 1–1.5 d |
| Interactive verification against real Nautilus/Dolphin/Thunar/PCManFM (blocked in *this* environment; needs a session where computer-use/GUI automation actually works, or manual testing), plus edge cases: very large file lists, non-UTF-8 filenames, rapid re-copy churn | 0.5–1 d |

This slightly exceeds the 5-day estimate already budgeted for `T-5.3.3`
mainly because of the X11 path, which `T-5.3.3`'s estimate may not have
priced in explicitly. Recommendation: either bump `T-5.3.3` by ~1–2 days, or
make an explicit scope call to ship Wayland-only clipboard interop for an
initial release and defer X11/XWayland support — worth a one-line decision
in `design.md` rather than leaving it implicit.

**G0 kill-criteria check:** S-2 has a workaround well under 10 days →
does **not** trigger the "reconsider the framework" kill criterion.
