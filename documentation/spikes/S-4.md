# Spike S-4: Directory Enumeration Throughput

| Field | Value |
|---|---|
| Spike ID | S-4 |
| Question | What's the fastest way to enumerate and stat large directories on Linux, and by how much? |
| Traces | NFR-03, NFR-04 (feeds T-3.1.1, T-3.1.2 acceptance criteria) |
| Status | Complete |
| Code | `spikes/s4-dir-enum/` (standalone Cargo project, not part of the main workspace) |

This is a timeboxed, non-UI, headless benchmark spike. Nothing here is production
code; it exists to pick a winning enumeration strategy and to sanity-check the
Phase 3 baseline numbers in `task.md` against real hardware before that work is
scheduled.

## 1. Method

### 1.1 Hardware / software

- CPU: AMD Ryzen 9 3900X (12C/24T)
- RAM: 62 GiB
- Kernel: Linux 6.18.39-1-MANJARO
- rustc 1.97.1, `rustix` 1.1.4, `rayon` 1.12.0, release profile (`opt-level=3`,
  `lto=true`, `codegen-units=1`)

### 1.2 Filesystems tested

Checked via `df -T` / `mount`; all three commonly-relevant Linux filesystems
were actually available on this machine, so all three were tested for real —
none faked:

| Label | Device | Mount | Notes |
|---|---|---|---|
| tmpfs | tmpfs | `/dev/shm` | RAM-backed |
| ext4 | `/dev/sda1` | `/run/media/meirk/storage_2` | spinning/SSD data volume |
| btrfs | `/dev/mapper/luks-...` (LUKS) | `/home` | CoW, root filesystem's `/home` subvolume |

### 1.3 Corpus generator

`spikes/s4-dir-enum/src/corpus.rs`: flat directories of 100,000 and
1,000,000 entries, deterministic from `(seed=1, index)` via a splitmix64
mix — same seed always reproduces the identical set of filenames and sizes.
File sizes are drawn from `{0, 0..512, 0..4096}` bytes so `statx` metadata
(`stx_size`) is non-trivial without inflating disk usage much (~768 MB for
1M entries, ~77 MB for 100k). Generation itself is parallelized across all
cores via `rayon`, each worker holding its own `openat` handle to the target
directory and creating files with `openat(dir_fd, name, O_CREAT|O_WRONLY, ...)`
— i.e. relative to a directory fd, not by rebuilding absolute paths per file.

Corpus generation time is not part of the benchmark result (it is a
one-time setup cost) but is logged for reference — see §4.

### 1.4 The three strategies (`spikes/s4-dir-enum/src/strategies.rs`)

All three use `rustix` raw syscalls, not `std::fs`, so the comparison
isolates the actual variable (whether/how you stat) rather than mixing in
`std::fs`'s own overhead:

1. **`naive`** — one `getdents64` scan (via `rustix::fs::RawDir`) to list
   names, then `statat(dir_fd, name, AT_SYMLINK_NOFOLLOW)` (full `struct
   stat`) on **every** entry, serially, even though the caller may not have
   needed it. This models the common mistake: stat-everything-unconditionally.
2. **`dtype`** — the same `getdents64` scan, but nothing else. `d_type` is
   already present in the kernel's dirent answer; when the caller only wants
   name + type (the `T-3.1.1` case), zero additional syscalls are issued.
3. **`statx` (parallel)** — one `getdents64` scan to collect names
   (unavoidable — you need the names before you can stat anything), then
   `statx(dir_fd, name, AT_STATX_DONT_SYNC | AT_SYMLINK_NOFOLLOW,
   STATX_BASIC_STATS)` for full metadata, batched across a `rayon` thread
   pool sharing one read-only directory fd. `AT_STATX_DONT_SYNC` skips
   forcing a synced view on network filesystems, which we don't need for
   local disks and don't want to pay for either.

All three time the *entire* pipeline (open dir → scan → stat, where
applicable) from `Instant::now()`, so the shared getdents scan cost is
counted identically in all three — this is a fair "wall clock to have names
[+ types] [+ full metadata] for every entry" comparison, not a
microbenchmark of stat alone. Every run computes a checksum (sum of
`st_size`/`stx_size`, or a d_type histogram) that is verified across runs
to catch any strategy silently doing less work.

### 1.5 Caveats

- **Warm cache.** There is no passwordless root on this machine, so
  `/proc/sys/vm/drop_caches` was not available; these are warm-page-cache,
  warm-dentry-cache numbers (each corpus is benchmarked immediately after
  being generated). This is the realistic case for repeat navigation in a
  file manager, but it is *not* a cold first-visit number — cold-cache
  numbers for spinning media in particular could be substantially worse.
  Flagging this explicitly since NFR-03/04 don't specify cache state.
- Corpus is flat (no subdirectories), per the spike's own scope ("flat is
  fine, deterministic from a seed").
- No symlinks/sockets/devices in the corpus, so `d_type` is always resolved
  by all three filesystems (no `DT_UNKNOWN` fallback path was exercised;
  the `dtype` strategy counts any `DT_UNKNOWN` it sees and none occurred).

## 2. Results

All times are wall-clock milliseconds for the *entire* strategy (dir open +
scan + stat as applicable) over the full corpus. `min` / `median` are over
5 repeated runs for the 100k corpus and 3 repeated runs for the 1M corpus
(fewer reps at 1M purely to keep the spike inside its timebox — variance
was already <5% at n=3). `statx` uses 24 worker threads (`nproc`).

### 2.1 100,000 entries

| Filesystem | Strategy | min (ms) | median (ms) | vs. naive |
|---|---|---:|---:|---:|
| tmpfs | naive | 141.2 | 141.8 | 1.0x |
| tmpfs | dtype | 27.7 | 28.1 | **5.1x** |
| tmpfs | statx (24T) | 33.9 | 35.9 | 3.9x |
| ext4 | naive | 160.4 | 162.5 | 1.0x |
| ext4 | dtype | 37.1 | 37.2 | **4.4x** |
| ext4 | statx (24T) | 45.2 | 46.0 | 3.5x |
| btrfs | naive | 154.8 | 175.8 | 1.0x |
| btrfs | dtype | 26.2 | 26.4 | **6.7x** |
| btrfs | statx (24T) | 37.8 | 41.1 | 4.3x |

### 2.2 1,000,000 entries

| Filesystem | Strategy | min (ms) | median (ms) | vs. naive |
|---|---|---:|---:|---:|
| tmpfs | naive | 1379.7 | 1409.8 | 1.0x |
| tmpfs | dtype | 271.8 | 276.1 | **5.1x** |
| tmpfs | statx (24T) | 322.9 | 334.8 | 4.2x |
| ext4 | naive | 1544.8 | 1547.5 | 1.0x |
| ext4 | dtype | 366.7 | 368.4 | **4.2x** |
| ext4 | statx (24T) | 425.6 | 449.5 | 3.6x |
| btrfs | naive | 1483.4 | 1490.8 | 1.0x |
| btrfs | dtype | 242.3 | 245.7 | **6.1x** |
| btrfs | statx (24T) | 312.4 | 332.2 | 4.7x |

### 2.3 Thread scaling for `statx` (tmpfs, 100k entries, min-of-3)

Checked separately since the winning full-metadata strategy's whole value
proposition is parallelism:

| Threads | min (ms) |
|---:|---:|
| 2 | 86.1 |
| 4 | 56.5 |
| 8 | 41.9 |
| 12 | 36.7 |
| 16 | 35.8 |
| 24 | 34.3 |

Scaling is clearly sub-linear past ~8-12 threads (syscall-bound, not
compute-bound — each `statx` is one syscall's worth of work, so beyond a
point adding threads just adds scheduling overhead for a mostly-serialized
kernel-side path). 12-16 threads captures essentially all the achievable
win; going to 24 threads is a rounding error's worth of extra gain. Worth
noting for `T-3.1.2`: an unbounded "use all cores" pool is not needed, and
oversubscribing may cost more (context-switch noise) than it buys on a
machine also running UI/other work.

## 3. Winning strategy

**There is no single winner — the right strategy depends on what the caller
actually needs, and that's the headline finding:**

- **Names + types only** (`T-3.1.1`'s use case — the initial listing paint):
  **`d_type`-aware `getdents64`, no `stat` at all.** This is the fastest
  strategy on every filesystem tested (4.2x-6.7x over naive), because it is
  the only one that does zero per-entry syscalls beyond the batch-amortized
  `getdents64` calls themselves. There is no reason to ever stat-everything
  unconditionally when only name/type is needed — this is confirmed, not
  theoretical, on this hardware.
- **Full metadata for every entry** (`T-3.1.2`'s use case — size/mtime
  columns, sort-by-size, etc.): **parallel batched `statx` with
  `AT_STATX_DONT_SYNC`**, 3.5x-4.7x faster than the naive serial
  `statat`-per-entry loop. It is slower than the `d_type`-only path (it is
  doing strictly more work — a real syscall per entry, just spread across
  cores), but it is the clear winner *within* the "I need full metadata"
  requirement.
- **Naive serial stat-every-entry is never the right choice** once `d_type`
  or parallel `statx` are available options, on any of the three
  filesystems. It should not appear anywhere in `LocalFs`'s hot path.

Practical recommendation for `T-3.1.1`/`T-3.1.2`: implement the `d_type`
fast path as the default for the initial chunked listing (matches
`ListOpts` requesting only name+type), and layer parallel `statx` on top,
driven by field requests, for anything that needs real metadata — exactly
the shape already described in the task table ("driven by `ListOpts` field
requests").

## 4. Corpus generation cost (reference only, not part of the benchmark)

| Filesystem | Count | Elapsed |
|---|---:|---:|
| tmpfs | 100,000 | 0.46 s |
| tmpfs | 1,000,000 | 4.5 s |
| ext4 | 100,000 | 2.2 s |
| ext4 | 1,000,000 | 29.3 s |
| btrfs | 100,000 | 4.1 s |
| btrfs | 1,000,000 | 41.2 s (and the subsequent `rm -rf` teardown of this one directory alone ran for several minutes in the background, far longer than ext4/tmpfs cleanup) |

Not a finding about enumeration (the thing this spike is scoped to), just
worth flagging in passing: btrfs was noticeably slower than ext4/tmpfs for
*writing and deleting* a million small files (CoW + metadata overhead on
create/unlink), even though its *enumeration* numbers were competitive with
(and on `dtype`, actually the fastest of) the three filesystems tested.
Creation/deletion and enumeration are different code paths with different
costs; this spike only measured the latter, which is the one that matters
for `NFR-03`/`NFR-04`.

## 5. Comparison against the Phase 3 baseline targets

From `task.md`:

- **`T-3.1.1`**: "100k entries enumerated (names + types only) in ≤ 60 ms on
  tmpfs; first chunk emitted in ≤ 5 ms"
- **`T-3.1.2`**: "Full metadata for 100k entries in ≤ 250 ms; requesting
  fewer fields measurably reduces time"

| Target | Measured (this spike) | Verdict |
|---|---|---|
| T-3.1.1: 100k names+types ≤ 60 ms (tmpfs) | **28.1 ms** median (`dtype`, tmpfs) | **Achievable with ~2x headroom.** Even ext4 (37.2 ms) and btrfs (26.4 ms) clear it; the target as stated is tmpfs-only and it's not close. |
| T-3.1.1: first chunk ≤ 5 ms | Not directly measured — this spike measures whole-directory completion, not chunked/streaming emission | **Not verified by this spike.** `T-3.1.1`'s own AC is about a *streaming* first-chunk latency, which requires the chunked-emission implementation itself (not built here) to measure. Flag as open for that task, not blocked by anything found here — 28 ms for the *whole* 100k directory strongly suggests a first chunk of a few thousand entries is comfortably sub-5ms, but this is inference, not a measurement. |
| T-3.1.2: full metadata for 100k ≤ 250 ms | **35.9-46.0 ms** median (`statx` parallel, all 3 filesystems) | **Achievable with large headroom (5-7x under budget).** Even the *naive* serial strategy (141-176 ms) would technically clear this specific target on all three filesystems, though it shouldn't be used — the point of `T-3.1.2`'s AC is presumably to force the parallel-and-field-selective design, not just to hit 250ms by any means. |
| T-3.1.2: fewer fields measurably reduces time | Not directly tested — this spike always requested `STATX_BASIC_STATS` (a fixed field set) | **Not verified by this spike**, but strongly plausible: `statx`'s whole design point is that the kernel can serve a subset of fields more cheaply on some filesystems, and the "correct" implementation described in `T-3.1.2` (`ListOpts`-driven field requests) is the mechanism to prove this — worth a follow-up micro-bench once that's built, comparing `STATX_BASIC_STATS` vs. `STATX_TYPE\|STATX_SIZE` alone. |

**Bottom line: both quantitative Phase 3 baseline targets look comfortably
achievable on this hardware, with 2-7x headroom.** The two AC clauses this
spike could not verify (first-chunk streaming latency, field-count-vs-time
sensitivity) aren't enumeration-throughput questions — they're properties
of the *implementation* of `T-3.1.1`/`T-3.1.2` themselves, and should be
measured directly when those tasks are built, not inferred from this spike.

## 6. What this spike does not answer

- Cold-cache / cold-disk performance (no root, couldn't drop caches).
- Nested/deep directory trees (recursive walk cost, as opposed to a single
  flat `readdir`).
- Network filesystems (SMB/SFTP/etc.) — `AT_STATX_DONT_SYNC` exists
  specifically for that case but there was nothing here to test it against.
- Memory cost of holding results (`EntryStore` SoA layout is a separate,
  unmeasured concern here — this spike only timed enumeration, not storage).
